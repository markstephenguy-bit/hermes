# Other MCP Gateway Candidates + ChatGPT Remote-MCP Auth Requirements

## Part A, Key Question 1: Is there an official Anthropic/OpenAI/Google/MCP-standards-org gateway or reference implementation for self-hosted custom upstreams?

### Takeaway
No. The MCP steering group (now under the Linux Foundation's Agentic AI Foundation, as of a December 2025 donation by Anthropic) publishes only **reference MCP *servers*** (`modelcontextprotocol/servers`) and a discovery **registry** (`modelcontextprotocol/registry`) — neither is a gateway/proxy/aggregator that fronts arbitrary custom upstream MCP servers for multiple clients. Anthropic's own "MCP tunnels" feature is about exposing a private server to Anthropic's own products, not a general-purpose gateway. No official Anthropic, OpenAI, or Google/DeepMind self-hosted MCP gateway product exists as of November 2026.

### Cited Findings
- Anthropic donated MCP itself to the newly formed Agentic AI Foundation (a Linux Foundation directed fund) in December 2025, co-founded by Anthropic, Block, and OpenAI, with Google/Microsoft/AWS/Cloudflare/Bloomberg support — meaning MCP the *protocol* is neutrally governed, but this is not a gateway product — [Anthropic news](https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation); [MCP blog](https://blog.modelcontextprotocol.io/posts/2025-12-09-mcp-joins-agentic-ai-foundation/); [GitHub blog](https://github.blog/open-source/maintainers/mcp-joins-the-linux-foundation-what-this-means-for-developers-building-the-next-era-of-ai-tools-and-agents/)
- The official `modelcontextprotocol/servers` repo is explicitly described as "a small number of reference servers maintained by the MCP steering group... intended as reference implementations to demonstrate MCP features and SDK usage" — i.e., example servers, not a gateway — [GitHub](https://github.com/modelcontextprotocol/servers)
- The official MCP Registry (`registry.modelcontextprotocol.io`, code at `github.com/modelcontextprotocol/registry`) is an "app store" style discovery API with Docker images at `ghcr.io/modelcontextprotocol/registry`, but "the official MCP Registry codebase is not designed for self-hosting, and the registry maintainers cannot provide support for this use case" — [modelcontextprotocol.io/registry/about](https://modelcontextprotocol.io/registry/about); [GitHub](https://github.com/modelcontextprotocol/registry)
- Anthropic's self-hosted "MCP tunnels" let an org run a lightweight gateway inside its private network that uses a Cloudflare Tunnel connector for outbound-only connectivity into Anthropic's products, layering mTLS + inner TLS + per-MCP-server OAuth — this is a private-network-access feature for Anthropic's own consuming products, not a general cross-client aggregator gateway — [DEV Community writeup](https://dev.to/thegatewayguy/anthropics-mcp-tunnels-and-self-hosted-sandboxes-keeping-agents-inside-your-perimeter-5a4d)
- No official Google/DeepMind MCP gateway product was found; Google's MCP involvement is client-side (Gemini CLI, Gemini API MCP support) and community servers, not a sanctioned gateway — [search sweep, no primary source found](https://www.google.com) (no primary citation available — see Gaps)

### Inferences
- Because the standards org's own registry explicitly disclaims self-hosting support, and the reference-servers repo is scoped to example servers, any "official, long-lasting" claim for a gateway product has to come from a third party building on top of the protocol (e.g., IBM's ContextForge, below) rather than from Anthropic/OpenAI/Google/the MCP org itself.

### Gaps
- Could not find a primary Google or DeepMind statement confirming the *absence* of an official gateway (absence-of-evidence, not evidence of absence) — treat "no official Google gateway found" as a search-coverage result, not a confirmed negative from Google itself.

## Part A, Key Question 2: Enterprise API-gateway-vendor MCP support (Kong, Apigee, etc.) that can be self-hosted

### Takeaway
Kong has a real, self-hostable MCP offering (via Kong Gateway Enterprise + the "AI MCP Proxy" plugin), but it is a paid/enterprise-plugin feature bolted onto Kong's existing API gateway, not a free-standing single-purpose MCP gateway — weakens it on "singular" (it's a whole API gateway platform) and on cost. No self-hostable Apigee MCP gateway was found.

### Cited Findings
- Kong's MCP Gateway capability is available in Kong Gateway Enterprise for "fully self-hosted deployments" and in Kong Konnect for hybrid/cloud; for fully on-prem, "you can install AI Gateway 2.x on-prem using Docker Compose" — [Kong AI Gateway docs](https://developer.konghq.com/ai-gateway/); [Speakeasy: managed vs self-hosted](https://www.speakeasy.com/resources/managed-vs-self-hosted-mcp-gateway)
- The "AI MCP Proxy" plugin "lets you connect any Kong-managed Service to [MCP]... translating between MCP and HTTP so that MCP-compatible clients can either call existing APIs or interact with upstream MCP servers through Kong" — [Kong AI MCP Proxy plugin docs](https://developer.konghq.com/plugins/ai-mcp-proxy)
- Kong's MCP Gateway is explicitly called out as "enterprise-only" leveraging paid plugins, and self-hosted Kong deployments "typically need additional security tooling layered on top for MCP-specific threat detection, as Kong's default threat model doesn't include MCP-specific threats like prompt injection through tool descriptions" — [Kong enterprise MCP gateway announcement](https://konghq.com/blog/product-releases/enterprise-mcp-gateway); [Speakeasy comparison](https://www.speakeasy.com/resources/managed-vs-self-hosted-mcp-gateway)
- Portkey (a newer AI-gateway vendor, not a legacy API-gateway vendor) also ships a self-hostable MCP Gateway: it is MIT-licensed, packaged in the same Docker deployment as its AI gateway with MCP and AI-gateway traffic on separate ports, and acts as "a proxy between MCP Clients and MCP servers, handling authentication, access control, and logging" so clients "authenticate once to Portkey" and it injects per-upstream credentials — [Portkey MCP gateway docs](https://portkey.ai/docs/product/mcp-gateway); [Portkey deployment docs](https://portkey.ai/docs/product/mcp-gateway/deployment). However, its latest tagged stable release (1.15.2) was published mid-January 2026 and the README already labels "Gateway 2.0" (with Portkey's expanded MCP scope) as prerelease — i.e., the MCP-specific capability set is still actively moving/unstable — [API7.ai comparison](https://api7.ai/ai-gateway-comparison)
- No evidence of a self-hostable Google Apigee MCP gateway was found in this pass.

### Inferences
- Both Kong's and Portkey's MCP capabilities are features of a broader general-purpose AI/API gateway rather than a dedicated single-purpose MCP gateway — they trade "singular, minimal footprint" for "powerful, already-deployed-elsewhere-in-the-org" if the household/org already runs Kong or Portkey for other API traffic. For a home-lab / single-purpose deployment (Hermes's context) this is likely heavier than needed.

### Gaps
- Could not verify current Kong AI MCP Proxy plugin pricing/licensing tier boundaries precisely (what exactly is gated behind Enterprise vs free Kong Gateway) from primary Kong docs in this pass — flagged as needing a follow-up read of Kong's own pricing page if this candidate is pursued further.

## Part A, Key Question 3: Other well-starred (500+ GitHub stars) self-hosted MCP gateways not already covered

### Takeaway
The one new candidate that clearly clears the 500-star bar and looks genuinely production-grade is **IBM's ContextForge (`IBM/mcp-context-forge`)** — roughly 4.6-4.7k GitHub stars, very active (3,000+ commits), single-container-deployable, with real auth/RBAC, OpenTelemetry observability, and virtual-server/hot-config features. Everything else found in this pass (`mcpproxy-go`, `MikkoParkkola/mcp-gateway`, `R0Wi/mcp-gateway`, `cuongdev/mcp-gateway`, "anythingmcp") is well under 500 stars and should be treated as a minor/early-stage project, not a serious long-term candidate.

### Cited Findings
- **IBM/mcp-context-forge ("ContextForge")**: described by IBM as "An AI Gateway, registry, and proxy that sits in front of any MCP, A2A, or REST/gRPC APIs, exposing a unified endpoint with centralized discovery, guardrails and management" — [GitHub](https://github.com/IBM/mcp-context-forge)
  - **Singular**: deployable as a single Docker/Podman container, or as a fuller Docker Compose stack (Postgres, Redis, Nginx) or Helm/Kubernetes — single-container mode exists but is the minimal option, not the only one — [GitHub README via fetch]
  - **Powerful**: JWT auth with JTI revocation, Basic auth, OAuth (Google/GitHub/Entra ID), user scoping, bearer-token forwarding for cross-gateway calls, admin bootstrap user; OpenTelemetry observability (Phoenix/Jaeger/Zipkin/OTLP), structured logging, health endpoints/metrics, web admin UI with live log viewer; Uvicorn auto-reload in dev mode plus a live admin dashboard — [GitHub README via fetch]
  - **Long-lasting**: ~4.7k stars / 957 forks / 3,359+ commits on main per one source — [search result, IBM GitHub]; a slightly different figure (4,640 stars, October 2026 snapshot) appears in a secondary source — [druce.ai vendor page](https://druce.ai/governance/wiki/vendors/ibm-contextforge) — both sources agree on "mid-4000s stars," actively committed to. Important caveat: the project explicitly disclaims being an official IBM product — "no official support from IBM or its affiliates" per third-party description — [search synthesis, needs primary-repo confirmation of exact disclaimer wording]
  - **Fast**: described as "pure proxy — no inherent LLM involvement... translates and routes tool calls; LLM reasoning happens in client applications" — [GitHub README via fetch]
  - **Cross-client**: supports custom/arbitrary MCP servers, REST/gRPC-to-MCP virtualization, and "A2A integration for external AI agents (OpenAI, Anthropic, custom)," positioned for multi-client use including Claude, ChatGPT, and Gemini via standard protocols (stdio, SSE, Streamable HTTP conversion) — [GitHub README via fetch]
- **mcpproxy-go** (`smart-mcp-proxy/mcpproxy-go`, a Go binary): star count is inconsistent across sources — one search pass reported 347, another reported 384 — both are well under the 500-star bar, so this does not meet the threshold being screened for, though it has genuinely interesting security features (tool quarantine against "Tool Poisoning Attacks," BM25-based tool search/filtering to fight context bloat, Docker isolation, OAuth auth, activity logging, "agent tokens") — [GitHub](https://github.com/smart-mcp-proxy/mcpproxy-go)
- **MikkoParkkola/mcp-gateway** (Rust, single binary, 100+ built-in API integrations): ~83 stars — below threshold — [GitHub](https://github.com/MikkoParkkola/mcp-gateway)
- **R0Wi/mcp-gateway** ("lightweight, self-hosted MCP aggregator gateway" with a "spec-compliant OAuth 2.1 authorization server"): ~0 stars at time of search — below threshold, very early-stage — [GitHub](https://github.com/R0Wi/mcp-gateway)
- **cuongdev/mcp-gateway** (TypeScript; OIDC auth, Casbin RBAC/ABAC, circuit breaking, PII redaction, 42-connector catalog, admin dashboard — feature list reads almost identically to larger projects): ~3 stars — below threshold; feature claims are disproportionate to adoption signal, worth flagging as a possible over-described side project rather than a proven candidate — [GitHub](https://github.com/cuongdev/mcp-gateway)
- **"anythingmcp"** ("self-hosted, source-available MCP gateway and API-to-MCP bridge"): ~200 stars per one aggregator source — below the 500-star bar — [search result synthesis — primary repo URL not independently confirmed in this pass, treat with caution]

### Inferences
- ContextForge is the standout new candidate: it is the only one in this sweep that combines 500+ stars, breadth of auth/observability features, confirmed pure-proxy architecture, and explicit multi-client/custom-upstream design — it deserves the same full side-by-side treatment given to MCPHub/MCPJungle/McpManager/mspstack/ToolHive/unified-mcp-gateway elsewhere in this research.
- All of the sub-500-star repos found here are consistent with "early/hobby project," not "long-lasting" by the criteria in this research; none should be promoted into the main comparison without a strong independent reason.

## Part B: ChatGPT's remote MCP / custom-connector authentication requirements (November 2026)

### Takeaway
ChatGPT does **not** require OAuth exclusively. As of November 2026, OpenAI's own custom-connector setup (Settings → Connectors → Create, consumer/Business product) and the separate Responses API "remote MCP server" tool each document multiple auth modes, and several sources — including a direct report of the live UI — describe **four** selectable options: **OAuth, "Access token / API key" (a static bearer token), No authentication, and a Mixed mode**. This means a self-hosted gateway using a simple static bearer token (the same scheme Claude Code and most of the gateways in this research use) is explicitly supported by ChatGPT's connector UI — not just OAuth — though OpenAI's own developer-facing API documentation leans heavily on OAuth language, which can make this non-obvious from a documentation-only read.

### Cited Findings
- OpenAI's developer guide for the Responses API's MCP tool states "the most common scheme is an OAuth access token. Provide this token using the `authorization` field of the MCP tool," and separately that "optional HTTP headers can be sent to the MCP server for authentication or other purposes" — i.e., the API-level docs frame OAuth as the primary/expected path but do leave room for raw headers — [OpenAI developer docs: MCP servers guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp); [platform.openai.com mirror](https://platform.openai.com/docs/guides/tools-connectors-mcp)
- OpenAI's "Add custom MCP server" developer guide documents that under Connection you set a Server URL (or select "Tunnel" for OpenAI's Secure MCP Tunnel for private/on-prem servers), then "configure authentication for your server," with named modes including "OAuth," "No authentication," and "OAuth or no authentication" (mixed); it also explicitly states "if your server expects a Bearer token in the Authorization header, set the Header Name to Authorization and the Value to Bearer <your-token>" — confirming a static-header path exists alongside OAuth — [OpenAI developer docs: Add custom MCP server](https://developers.openai.com/api/docs/guides/custom-mcp-server)
- OpenAI's official **ChatGPT help-center** article "Connecting custom MCP servers in ChatGPT" (https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt) is the authoritative consumer-facing source, but returned HTTP 403 to automated fetch in this research pass; its content was only accessible via search-engine snippet, which states: custom MCP server connections / full MCP support are available to **ChatGPT Business and Enterprise/Edu** customers on ChatGPT web, while **Pro** users can connect custom MCP servers but limited to **read/fetch permissions only**; setup is via ChatGPT Plugins → "+" → "Add custom MCP server," entering Server URL (or Tunnel), configuring auth, and accepting a risk warning ("I understand and want to continue") — [help.openai.com via search snippet](https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt) — **flagged: snippet-only, not a direct primary fetch; recommend re-fetch with an authenticated/browser-based tool if exact tier wording matters.**
- Multiple independent secondary sources describe the live "Settings → Connectors → Create" (or "Settings → Apps → New App") dialog as offering four authentication choices — **OAuth, Access token / API key, No Auth, and Mixed** — with the API-key option attaching "a fixed `Authorization: Bearer <token>` to every MCP request — no OAuth, no JWT, no JWKS" — [GitHub issue, agentfront/frontmcp #544](https://github.com/agentfront/frontmcp/issues/544) (reporter's direct, unverified-by-OpenAI observation); corroborated independently by a separate search-engine synthesis citing "Bearer token" as a selectable method with the raw token entered in the UI — [search synthesis, no single stable primary URL captured]
- Contradicting/qualifying note: a vendor integration doc (Holistics) that walks through connecting their own MCP server to ChatGPT only shows and instructs users to "select **OAuth** as the authentication method," without describing or ruling out the other options — consistent with OAuth being the default/recommended choice in official written walkthroughs even where other modes exist in the UI — [Holistics docs](https://docs.holistics.io/docs/ai/mcp-server/chatgpt)
- A real, OpenAI-acknowledged **compatibility issue** was found on OpenAI's own developer community forum: a reporter claimed ChatGPT's MCP connector violated the MCP Authorization spec by directly requesting `/.well-known/oauth-authorization-server` and `/.well-known/openid-configuration` rather than following the spec's documented 401-triggered discovery sequence; the resolution thread clarifies this is spec-legal (RFC 9728 permits discovering metadata "by any means," making the `WWW-Authenticate` header route optional, not mandatory) but also notes "OpenAI's team subsequently updated the connector to automatically discover required scopes from the `WWW-Authenticate` header during initial connection, addressing related scope issues" — i.e., early versions of ChatGPT's OAuth discovery flow caused real integration friction for self-hosted OAuth-protected MCP servers, since fixed — [OpenAI Developer Community thread](https://community.openai.com/t/new-mcp-connector-does-not-follow-mcp-authorization-spec/1358992)
- OpenAI documents a **Secure MCP Tunnel** specifically so a private/on-prem/behind-NAT MCP server (exactly Hermes's home-lab situation) can be connected "without exposing the server to the public internet," as an alternative to requiring a publicly-reachable HTTPS endpoint — [developers.openai.com custom-mcp-server guide](https://developers.openai.com/api/docs/guides/custom-mcp-server)
- Transport requirement: ChatGPT's remote MCP support is for **SSE and Streamable HTTP** transports (not stdio) — consistent across the developer guide and the custom-mcp-server guide — [developers.openai.com guides](https://developers.openai.com/api/docs/guides/tools-connectors-mcp)

### Inferences
- The practical takeaway for comparing gateway candidates: a self-hosted MCP gateway that exposes a simple static bearer token over HTTPS (the common pattern for MCPHub/MCPJungle/ToolHive/etc.) should be connectable to ChatGPT via the "Access token / API key" connector mode — OAuth is not a hard requirement, contrary to a surface read of OpenAI's API-level docs which foreground OAuth language. The gating factors are more about **account tier** (Business/Enterprise/Edu for full read-write MCP; Pro capped to read/fetch) and **network reachability** (public HTTPS or OpenAI's Secure MCP Tunnel) than about auth scheme.
- Early ChatGPT MCP OAuth-discovery behavior caused real friction for self-hosted OAuth-protected servers (the well-known-endpoint ordering issue); OpenAI has since patched this, but it's a documented sign that ChatGPT's MCP client implementation has been a moving target — worth re-verifying behavior empirically with any OAuth-based gateway before relying on it, rather than assuming spec compliance from docs alone.

If this detail is load-bearing for a final recommendation, it should be re-confirmed via a logged-in browser session or an alternate fetch method.

- Did not test any gateway candidate's actual connector-setup flow against a live ChatGPT account — all findings are desk research against documentation and community reports, not hands-on verification.
