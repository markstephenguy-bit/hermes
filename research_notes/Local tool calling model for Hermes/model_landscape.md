# Small-to-Mid Open-Weight LLMs for Tool/Function Calling (as of October 2026)

## Which specific models are currently cited as strong for function/tool-calling as of 2026, ideally with BFCL/Gorilla scores?

### Takeaway
Qwen3 (4B/8B/14B/30B-A3B), GLM-4-9B, Mistral Small 3.2/Ministral 3, and the older but still-cited Llama-3-Groq-8B-Tool-Use are the names that recur most as strong small/mid tool-callers; Qwen3 in particular is repeatedly described as the most stable default for local agentic tool use in 2026 community guidance. The Berkeley Function-Calling Leaderboard moved to a v4, more agentic/multi-turn format in April 2026, which several older scores (e.g. Llama-3-Groq's 89%) predate and are not directly comparable to.

### Cited Findings
- BFCL v4 (released April 2026) shifted to a more holistic agentic evaluation, scoring whether a model picks the right function and fills valid parameters, including multi-turn; the gap between frontier closed APIs and the top open-weight models has closed to roughly 3-4 percentage points overall — [Spheron Network BFCL v4 guide](https://www.spheron.network/blog/tool-calling-benchmarks-bfcl-tau-bench-latency-optimization/)
- On BFCL v4, Mistral Small (the ~24B "Mistral Small 4" generation) scored ~72% overall (~76% single-turn, ~68% multi-turn); Llama 4 Scout (17B active, MoE) scored ~68% overall (~72% single-turn, ~63% multi-turn) — [Spheron Network BFCL v4 guide](https://www.spheron.network/blog/tool-calling-benchmarks-bfcl-tau-bench-latency-optimization/)
- Qwen3-8B and Qwen3-14B use the "hermes" tool-call parser format and support native function-calling (FC) mode; when trained on reasoning-enhanced tool-use data, Qwen3-14B surpassed several larger open- and closed-source models on BFCL-v4, with gains concentrated in multi-turn/agentic evaluations — [ToolMind Technical Report](https://arxiv.org/pdf/2511.15718)
- Community/production guidance: "Across community testing, Qwen3 has the most stable tool calling," and Qwen3-14B is called out as "most reliable for tool calls per GB" fitting 12-16GB cards, while Qwen3-8B is "best on 8-12GB with great speed/quality balance for ~5 tools" — [tomodahinata.com Qwen3-8B agent writeup](https://tomodahinata.com/en/blog/qwen3-agent-tool-use-function-calling-qwen-agent-production)
- GLM-4-9B-Chat scored 80.26 (AST Summary), 84.40 (Exec Summary), 87.92 (Relevance), 81.00 overall on the (pre-v4) Berkeley Function Call Leaderboard, and is stated to "significantly outperform Llama-3-8B-Instruct," with its function-call capability "aligned with GPT-4 Turbo (2024-04-09)" — [THUDM/glm-4-9b-chat README](https://huggingface.co/THUDM/glm-4-9b-chat/blob/main/README_en.md)
- Llama-3-Groq-8B-Tool-Use (a Groq finetune of Llama 3 8B, released July 2024) scored 89.06% overall accuracy on the (older, pre-v4) Berkeley Function Calling Leaderboard, described at the time as the best-performing open-source 8B model on BFCL — [MarkTechPost, Groq release announcement](https://www.marktechpost.com/2024/07/18/groq-releases-llama-3-groq-70b-tool-use-and-llama-3-groq-8b-tool-use-open-source-state-of-the-art-models-achieving-over-90-accuracy-on-berkeley-function-calling-leaderboard/); 2026 community review still cites this score but calls the model "narrow — a function-calling scalpel, not a general reasoner" with a tight 8K context window — [localaimaster.com, Best Ollama Models for AI Agents 2026](https://localaimaster.com/blog/best-ollama-models-for-agents)
- Qwen3.5-9B (9.7B dense) is cited with 66.1 on BFCL-V4 and 79.1 on TAU2-Bench — [vdf.ai, Best Local LLM for Agents and Tool Calling (2026)](https://vdf.ai/blog/best-local-llm-for-agents-tool-calling/)
- Granite 4.2 8B (8.8B dense, IBM) is cited with 52.39 on BFCL v4 and 66.34 on τ³-bench — [vdf.ai, Best Local LLM for Agents and Tool Calling (2026)](https://vdf.ai/blog/best-local-llm-for-agents-tool-calling/)
- Qwen3-Coder-30B-A3B-Instruct (30B total/3B active MoE) scored BFCL-v3 69.1, TAU1-Retail 61.7, TAU1-Airline 32.0, TAU2-Retail 34.2; a related figure shows Qwen3-30B-A3B scoring only 26% (thinking mode) / 10% (instruct mode) on τ²-Bench Telecom, suggesting large variance by benchmark/domain — [Qwen3-30B-A3B HF model card and apxml.com spec page](https://apxml.com/models/qwen3-30b-a3b)
- Mistral Small 3.2 (24B) improved multi-turn tool-use reliability on BFCL v2 to ~78% (up from ~71% for Small 3.1), and cut its "infinite generation" failure rate from 2.11% to 1.29%, attributed to reworked tokenizer-side tool-schema handling — [MarkTechPost, Mistral Small 3.2 release](https://www.marktechpost.com/2025/06/21/mistral-ai-releases-mistral-small-3-2-enhanced-instruction-following-reduced-repetition-and-stronger-function-calling-for-ai-integration/)
- Phi-4-Mini-Instruct (3.8B) scored only 31.3% on BFCL-v3 at release, but newer out-of-the-box measurements put it in the "low-to-mid 80s" on BFCL v4 — these two scores are not from the same benchmark version and shouldn't be compared directly — [benchmarklist.com Phi-4-Mini](https://benchmarklist.com/models/microsoft-phi-4-mini-instruct/); [ertas.ai on-device tool-calling comparison](https://www.ertas.ai/blog/on-device-tool-calling-2026-qwen3-gemma4-phi4)
- MiniCPM4 (8B) is reported with function-name accuracy of 88.3% and parameter-name accuracy of 76.1% on its own MCP tool-calling evaluation, stated to outperform baseline Qwen3-8B on these metrics and to exceed GPT-4o on name/param/value accuracy for its MiniCPM4-MCP variant — [neurohive.io MiniCPM4 coverage](https://neurohive.io/en/state-of-the-art/minicpm4-open-local-model-achieves-qwen3-8b-performance-with-7x-inference-acceleration/) (Note: this is the model author's own benchmark, not an independent third-party leaderboard — treat with more caution than BFCL numbers.)
- xLAM-2-8b-fc-r (Salesforce's function-calling-specialized finetune family) reached 46.68% on BFCL-V4 per one secondary source, well below the dense general-purpose models above — [vdf.ai via search synthesis](https://vdf.ai/blog/best-small-language-models/); the much larger xLAM-2-70b-fc-r reaches 56.2% on τ-bench vs 52.9% for GPT-4o, and vs 38.2% for base Llama 3.1 70B Instruct — [Salesforce xLAM-2 blog](https://www.salesforce.com/blog/xlam-large-action-models-v2/)

### Inferences
- BFCL scores from before the April 2026 v4 revision (Llama-3-Groq's 89%, GLM-4-9B's 81%, Phi-4-Mini's 31.3%) are not comparable to v4-era scores (Qwen3.5-9B's 66.1, Granite 4.2 8B's 52.39) — v4 appears to be meaningfully harder/more agentic. Any shortlist for Hermes should prefer v4-era scores where available and treat pre-v4 scores as directionally informative only.
- Dense general-instruction models in the 8-14B class (Qwen3 family, GLM-4-9B, Mistral/Ministral) now appear to out-perform dedicated "function-calling-only" finetunes like xLAM-2-8B on holistic agentic benchmarks — specialization on narrow single-call accuracy doesn't seem to transfer to multi-turn agent-loop reliability as well as broad instruction-tuned models with native tool-call training.
- Qwen3 shows up independently across nearly every source (benchmark papers, vendor docs, community leaderboards, llama.cpp/vLLM tooling) as the safest current default for local agentic tool-calling across the whole 1B-30B range, which is corroborating signal beyond any single benchmark number.

### Gaps
- No access to the live, interactive Gorilla/BFCL leaderboard table itself (gorilla.cs.berkeley.edu/leaderboard.html) — the page's JS-rendered table wasn't retrievable via fetch, so exact current rank-ordered scores for every small model (e.g. exact Qwen3-8B, Qwen3-14B, Gemma 4 BFCL-v4 numbers) could not be independently confirmed from the primary source; figures above come from secondary aggregators and vendor/community writeups.
- Gemma 4 (Google's 2026 release, including an "E4B" edge variant) is repeatedly mentioned as function-calling capable but no vetted third-party BFCL v4 score was found for it specifically — only an informal "mid-to-high 80s" estimate from a single blog's own internal eval.

## For each strong candidate, what is the parameter count, and what is the approximate file size / VRAM requirement at Q4_K_M and Q8_0 quantization?

### Takeaway
At Q4_K_M, models in this class need roughly 0.55-0.6 GB of VRAM per billion parameters (plus KV-cache overhead), so dense models up to ~14B fit comfortably in 16GB with headroom for context, while Q8_0 roughly doubles that footprint and starts to use most of a 16GB budget even for an 8B model once KV cache and OS overhead are included.

### Cited Findings
- Qwen3 8B: Q4_K_M GGUF file ≈ 5.03 GB; runtime VRAM at Q4_K_M ≈ 4.9 GB; recommended ≥11 GB VRAM "for the best balance of quality and speed" (implying headroom for longer context/KV cache) — [willitrunai.com Qwen3 8B page](https://willitrunai.com/models/qwen-3-8b)
- Qwen3 14B: Q4_K_M file size reported as either 9.00 GB or 8.38 GB depending on the measuring source; VRAM requirement at Q4_K_M ≈ 9.50 GB, with practical recommendation of "roughly 10 to 11 GB of VRAM at an 8K context" — [willitrunai.com Qwen3 14B page](https://willitrunai.com/models/qwen-3-14b); [modelfit.io Qwen3-14B quant comparison](https://modelfit.io/quant-compare/qwen3-14b/)
- Qwen3 14B: Q8_0 GGUF file size ≈ 15.7-15.8 GB (near-lossless, described as "generally unnecessary" given the size) — [search synthesis of multiple Qwen3-14B-GGUF HF repos, e.g. OMP123/Qwen3-14B-Q8_0-GGUF](https://huggingface.co/OMP123/Qwen3-14B-Q8_0-GGUF)
- General GGUF rule of thumb: Q4_K_M file size in GB ≈ parameter count (billions) × ~0.6; for a 7-8B model specifically, Q4_K_M ≈ 3.8-4.6 GB, Q5_K_M ≈ 4.5-5.3 GB, Q8_0 ≈ 6.7-8.0 GB — [willitrunai.com quantization guide](https://willitrunai.com/blog/quantization-guide-gguf-explained); [eastondev.com Ollama GGUF guide](https://eastondev.com/blog/en/posts/ai/20260422-ollama-gguf-quantization/)
- Q4_K_M uses roughly 43% less VRAM than Q8_0 "at a small quality cost," per the same quantization-size synthesis above — [willitrunai.com Qwen3 blog summary]
- Qwen3.5-9B (dense): 4-bit quantized file ≈ 5.6 GB — [vdf.ai, Best Local LLM for Agents and Tool Calling (2026)](https://vdf.ai/blog/best-local-llm-for-agents-tool-calling/)
- Granite 4.2 8B (dense, 8.8B params): 4-bit file ≈ 5.4 GB — [vdf.ai, Best Local LLM for Agents and Tool Calling (2026)](https://vdf.ai/blog/best-local-llm-for-agents-tool-calling/)
- Ministral 3 14B (13.9B params): 4-bit file ≈ 8.2 GB — [vdf.ai, Best Local LLM for Agents and Tool Calling (2026)](https://vdf.ai/blog/best-local-llm-for-agents-tool-calling/)
- Llama-3-Groq-8B-Tool-Use: Q4_K_M ≈ 4.7-4.8 GB — [localaimaster.com, Best Ollama Models for AI Agents 2026](https://localaimaster.com/blog/best-ollama-models-for-agents)
- Hermes 4 14B (Nous Research finetune, dense): Q4 quant ≈ 9-10 GB — [localaimaster.com, Best Ollama Models for AI Agents 2026](https://localaimaster.com/blog/best-ollama-models-for-agents)
- MiniCPM4 ships in 0.5B and 8B parameter sizes, explicitly optimized for edge/end-device deployment with claimed up to "7x inference acceleration" versus comparable models — [neurohive.io MiniCPM4 coverage](https://neurohive.io/en/state-of-the-art/minicpm4-open-local-model-achieves-qwen3-8b-performance-with-7x-inference-acceleration/)

### Inferences
- For a 16GB GPU budget, Q4_K_M is the practical ceiling for any dense model above ~14B, and Q8_0 is realistic only up to roughly 8-10B dense before KV cache/context eats the remaining headroom — a 14B model at Q8_0 (≈15.7GB) would leave almost no room for context on a 16GB card.
- Across every dense 8-14B model surveyed, Q4_K_M file size consistently lands close to "params(B) × 0.55-0.65 GB," so this ratio is a reasonable quick estimator for any model not explicitly measured above.
- Small MoE models (Qwen3-30B-A3B class, 30B total/3B active) have total-parameter storage requirements (weights must all be loaded into VRAM even though only ~3B are "active" per token) that are closer to a dense 30B model's Q4_K_M footprint (~18-20GB) than to a dense 3B model — meaning they do NOT obviously fit a 16GB budget despite the "3B active" framing, unless more aggressive quantization or CPU-offload of experts is used. This needs validation against actual Qwen3-30B-A3B GGUF file sizes, which were not directly retrieved in this research pass.

### Gaps
- Did not retrieve a hard number for Qwen3-30B-A3B's actual Q4_K_M GGUF file size (total weights, not just "active" params) — needed to confirm whether this MoE model genuinely fits under a 16GB budget or requires partial CPU offload.
- Did not retrieve exact GGUF/quantized file sizes for GLM-4-9B, Mistral Small 3.2 (24B — likely too large for 16GB even at Q4), Ministral 3 8B/3B tiers, Gemma 4/4B, or MiniCPM4-8B specifically at Q4_K_M/Q8_0 — only some of these were found (see Cited Findings); the rest would need direct HuggingFace GGUF repo lookups (e.g. bartowski or unsloth quant repos) in a follow-up pass.
- Mistral Small 3.2 and "Mistral Small 4" are 24B-class models, outside the strict 1-16B window, but are frequently cited in tool-calling comparisons alongside smaller models — flagged here for completeness since BFCL discussion often groups them together, but they likely do not fit a 16GB VRAM budget at any reasonable quant (24B at Q4_K_M ≈ 14-15GB alone, before context).

## Are there specific models in the 7B-16B dense class, or small MoE class (under ~16B total/active params), that reviewers suggest are "good enough" substitutes for a 30B+ model for routine agentic tool-calling?

### Takeaway
Multiple 2026 community sources explicitly frame Qwen3-8B/14B and similarly-sized dense models as "good enough" stand-ins for larger models specifically for tool-calling (as opposed to deep reasoning), on the logic that well-scoped single- and few-tool agent loops don't require the extra capacity that long multi-step planning or complex reasoning does.

### Cited Findings
- "For most people in 2026, the best Ollama model for AI agents is Qwen3 8B — it needs roughly 5 GB of weights at Q4_K_M, carries Ollama's native Tools capability, and comes from a family with published function-calling scores" — [localaimaster.com, Best Ollama Models for AI Agents 2026](https://localaimaster.com/blog/best-ollama-models-for-agents)
- Qwen3 14B is characterized as "most reliable for tool calls per GB," explicitly for GPUs in the 12-16GB range, positioned as the practical sweet spot rather than reaching for a 30B+ model — [tomodahinata.com Qwen3-8B/14B agent production writeup](https://tomodahinata.com/en/blog/qwen3-agent-tool-use-function-calling-qwen-agent-production)
- Hardware-tiered 2026 recommendation explicitly separates workloads: "Qwen3.6-35B-A3B or GLM-4.7-Flash on a 24-32GB GPU, Qwen3.5-9B on 8-16GB" — implying the 8-16GB tier is expected to use ~9B-class dense models rather than needing larger MoE models, for routine agent work — [localaimaster.com, Best Ollama Models for AI Agents 2026 synthesis]
- MiniCPM4 (8B) is explicitly marketed/benchmarked as matching Qwen3-8B-level quality while being far more inference-efficient, aimed at edge/end-device deployment rather than a cloud-scale model — [neurohive.io MiniCPM4 coverage](https://neurohive.io/en/state-of-the-art/minicpm4-open-local-model-achieves-qwen3-8b-performance-with-7x-inference-acceleration/)
- Llama-3-Groq-8B-Tool-Use is positioned as a narrow specialist that can match or exceed much larger general models purely on function-calling accuracy, at the cost of being "not a general reasoner" — i.e., a credible substitute specifically for the tool-calling slice of agentic work — [localaimaster.com, Best Ollama Models for AI Agents 2026](https://localaimaster.com/blog/best-ollama-models-for-agents)
- GLM-4-9B-Chat's function-call capability was described as matching GPT-4 Turbo (April 2024 snapshot) despite being a 9B open model — an early (2024) data point for the "small model good enough for tool-calling" thesis that predates the 2026 models above but is the origin of GLM's reputation in this niche — [THUDM/glm-4-9b-chat README](https://huggingface.co/THUDM/glm-4-9b-chat/blob/main/README_en.md)

### Inferences
- The recurring framing across sources is a two-tier mental model: dense 8-14B models (Qwen3-8B/14B, GLM-4-9B, Granite 4.2 8B, Qwen3.5-9B) for routine/well-scoped tool-calling, vs. 30B+ dense or larger-MoE models reserved for long multi-step planning or complex reasoning chains — this matches Hermes's own stated local-model role (tool-execution "working" tier vs. a separate "thinking" tier) per prior project memory.
- No source claimed a sub-7B model (e.g. Phi-4-mini at 3.8B, Qwen3-4B) is a reliable full substitute for a 30B+ model even for routine tool-calling — the "good enough" claims cluster at 8B and above, with 4B-class models positioned as weaker fallbacks for load-bearing agentic work.

### Gaps
- No direct side-by-side benchmark was found comparing e.g. Qwen3-14B's BFCL v4 score against Qwen3-30B-A3B's or a 30B+ dense model's score on the same test set — the "good enough" framing in sources is qualitative/community consensus rather than a controlled head-to-head number.

## Known weaknesses of smaller models for tool-calling (argument formatting, multi-step chaining reliability) relevant to an agent harness executing real tools

### Takeaway
The dominant failure mode across sources is that small formatting mistakes (wrong argument name/type/value, malformed JSON, hallucinated function names) invalidate an entire tool call, and in multi-turn agent loops these errors compound into repeated failures ("death spirals") rather than being self-corrected — this is the central risk for a harness that executes real tools rather than just scoring single calls.

### Cited Findings
- "A single incorrect argument or slightly malformed JSON object can cause a tool call to fail, and in multi-turn scenarios where a task requires a sequence of tool calls, such failures often lead to a 'death spiral'" — [arXiv 2607.05775, Beyond the Leaderboard: tool-use/planning/reasoning failure synthesis](https://arxiv.org/pdf/2607.05775)
- "After a failure the model often repeats the same mistake in multi-turn interactions" and LLM tool-use errors recur in seven categories: insufficient API calls, incorrect argument values, incorrect argument names, incorrect argument types, redundant/repeated API calls, hallucinated function names, and invalid output formatting — [arXiv 2607.05775 synthesis](https://arxiv.org/pdf/2607.05775)
- Typical concrete failure example cited: a model providing a place name where latitude/longitude values are schema-required, or generating arguments that violate schema constraints outright — [search synthesis, Failure Makes the Agent Stronger paper family](https://arxiv.org/html/2509.18847v3)
- Single-call/single-turn benchmark scores "overstate agent skill" relative to real multi-turn use, per the vdf.ai comparison table, which explicitly separated single-turn from multi-turn BFCL v4 figures (e.g. Mistral Small: 76% single-turn vs 68% multi-turn; Llama 4 Scout: 72% vs 63%) — [Spheron Network BFCL v4 guide](https://www.spheron.network/blog/tool-calling-benchmarks-bfcl-tau-bench-latency-optimization/); [vdf.ai, Best Local LLM for Agents and Tool Calling (2026)](https://vdf.ai/blog/best-local-llm-for-agents-tool-calling/)
- "Small models handle well-scoped tools well; long multi-step plans still favour larger models" — explicit statement that the single-call/few-tool case is where small models are safe, but plan length/complexity is where they degrade — [vdf.ai, Best Local LLM for Agents and Tool Calling (2026)](https://vdf.ai/blog/best-local-llm-for-agents-tool-calling/)
- Mistral Small's jump from Small 3.1 to 3.2 specifically targeted this class of problem: the 3.1 parser was described as "finicky," and 3.2 reworked tokenizer-side tool-schema handling so the model better respects required-vs-optional argument distinctions and produces cleaner JSON across multi-turn conversations, cutting "infinite generation" failures from 2.11% to 1.29% — [MarkTechPost, Mistral Small 3.2 release](https://www.marktechpost.com/2025/06/21/mistral-ai-releases-mistral-small-3-2-enhanced-instruction-following-reduced-repetition-and-stronger-function-calling-for-ai-integration/)
- There are "corner cases where tool calls are generated but they are malformed and cannot be parsed" even with Qwen3's generally stable tool-calling; the recommendation for production code is that the application itself should defensively attempt to parse/validate rather than trust the model's output format — [search synthesis on Qwen3/Qwen-Agent tool calling](https://qwen.readthedocs.io/en/latest/framework/function_call.html)
- Native function-call special tokens (used by e.g. Gemma 4) reduce output token count for typical tool calls by about 15-20% compared to JSON-formatted tool calls, which can reduce surface area for formatting errors and lowers latency — [ertas.ai, on-device tool-calling comparison](https://www.ertas.ai/blog/on-device-tool-calling-2026-qwen3-gemma4-phi4)
- After light QLoRA fine-tuning (rank 32, 3 epochs, 600 examples) on a narrow customer-support tool-calling task, Phi-4-Mini, Gemma 4 E4B, and Qwen3-4B all converged to ~95% joint accuracy, suggesting base-model formatting weaknesses are substantially correctable with small amounts of task-specific fine-tuning rather than being an inherent ceiling — [ertas.ai, on-device tool-calling comparison](https://www.ertas.ai/blog/on-device-tool-calling-2026-qwen3-gemma4-phi4)
- A known infrastructure-level (not model-level) gotcha: llama.cpp's server returns HTTP 500 instead of a 4xx when a client supplies malformed tool-call arguments, which matters for how an agent harness should detect and handle tool-call-format failures distinctly from genuine server errors — [ggml-org/llama.cpp GitHub Issue #25510](https://github.com/ggml-org/llama.cpp/issues/25510)

### Inferences
- For Hermes's harness (which executes real tools: code execution, browser automation, file edits), the practical implication is that the harness itself — not just model choice — needs defensive JSON/schema validation and retry logic around tool calls, since even "stable" models like Qwen3 produce occasional malformed calls, and once one call in a chain fails, smaller models are prone to repeating rather than correcting the mistake.
- Given the strong fine-tuning result (base models converging to ~95% on a narrow task after light QLoRA), if Hermes has a well-defined, limited tool surface, a 4-8B model fine-tuned on that specific tool schema may out-perform a larger untuned general model — this is a concrete alternative to simply picking a bigger base model.
- Longer/more complex multi-step tool chains are the main scenario where 7-16B models should be expected to need the most defensive scaffolding or fallback-to-larger-model escalation, consistent with Hermes's existing local-model-as-"working tier" design (escalating to a "thinking tier" for harder cases).

### Gaps
- No source gave a quantitative comparison of malformed-call rate specifically broken out by model size within the 7-16B band (e.g., is Qwen3-14B meaningfully less error-prone than Qwen3-8B on argument formatting specifically, independent of overall BFCL score?) — available data conflates "overall accuracy" with pure formatting-error rate.
- No direct evidence was found on how well any of these specific small models handle long tool-chaining (5+ sequential calls) under a real code-execution/browser-automation harness like Hermes's — the cited failure modes are from benchmark/academic settings (BFCL, MCP-Bench, travel-planning benchmarks), not from a report of this specific type of harness.
