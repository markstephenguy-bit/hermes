# Right-sizing a local LLM for routine tool-calling with cloud escalation

## Are small-local + large-cloud escalation architectures a documented, common pattern for AI agents?

### Takeaway
Yes — the pattern (cheap/local model handles routine turns, escalates to a frontier cloud model on failure or detected complexity) is widely discussed in 2026 engineering and community writing, but most public writeups describe the *architecture* in general terms rather than publishing hard, numeric "good enough" criteria for the local model; the few projects that give real numbers are small-model tool-calling benchmarks rather than full agent-harness case studies.

### Cited Findings
- A personal local-first setup runs Qwen 2.5 (described by the author as "impressive for its size" but "still a relatively small model") as the primary agent; "the local model first attempts the task on its own. If it fails, it retries. If it still cannot solve the problem, it escalates the issue to Claude with only the information needed to move forward." — [My local LLM can call Claude when it's stuck](https://www.xda-developers.com/local-llm-call-claude-changed-everything-local-first-setup/)
- The same piece does not specify how "stuck" is actually detected (test failures vs. confidence threshold vs. retry-count limit) — it is a conceptual outline, not a technical spec, as multiple commenters on the piece note. — [My local LLM can call Claude when it's stuck](https://www.xda-developers.com/local-llm-call-claude-changed-everything-local-first-setup/)
- General routing-layer tooling (e.g., LiteLLM) is used to let a harness swap between local and cloud models without rebuilding the agent, and "a small router model can sit in front to classify the request, pick the tool, and decide whether the job is done or whether it needs to escalate to a bigger model." — [Router model: Stop Sending Every Request to Your Biggest LLM](https://www.innoscale.net/a-small-router-model-should-decide-what-your-big-model-sees/)
- Cognition's Devin CLI supports "start local, hand off to the cloud" — but this is session/compute handoff (moving the same frontier model's execution to more capacity when "the work outgrows your laptop"), not model-tiering between a small local model and a large cloud model; Devin CLI still lets the user pick frontier models (Opus 4.7, GPT-5.5, Cognition's SWE-1.6) regardless of where execution happens. No specific escalation threshold is documented — it is described as developer-discretionary. — [Devin CLI: Start Local, Hand Off to the Cloud](https://cognition.com/blog/devin-for-terminal)
- 2026 "agent harness" commentary converges on the same pattern at a conceptual level: "good harnesses route simple tasks to cheap models, complex tasks to expensive ones," with fallback chains that "after N failures, route to a human operator." One example cited: "a small model went from failing a planning task completely to passing it completely, on the strength of a single change to the shell around it, with the weights untouched" — i.e., harness/scaffolding quality can matter as much as model tier. — [Agent = Model + Harness](https://cobusgreyling.substack.com/p/agent-model-harness); [Human-in-the-Loop Escalation Design for AI Agents 2026](https://www.digitalapplied.com/blog/human-in-the-loop-escalation-design-ai-agents-2026)
- In the academic LLM-routing literature, the field distinguishes two architectures relevant to this pattern: **routing** (a classifier picks one model up front based on intent/complexity — low latency overhead, ~2–8ms for embedding-based routers, single model hop) vs. **cascading** (always try the cheap model first, run a verifier, escalate only on verifier failure — guarantees an accuracy floor but pays for the cheap model + verifier on every request, and "even a small escalation rate of 1–3% can erase most cascade savings"). — [LLM Routing and Model Cascades: How to Cut AI Costs Without Sacrificing Quality](https://tianpan.co/blog/2025-11-03-llm-routing-model-cascades); cross-referenced via [Why LLM Cascades Fail for Interactive Apps — Use Router](https://dev.to/nainikmehta/why-llm-cascades-fail-for-interactive-apps-use-router-leg)
- Industry recommendation for implementation order in a tiered agent system: (1) semantic caching first ("simplest win"), (2) intent-based routing for well-defined categories, (3) confidence-based cascading for ambiguous middle cases, (4) fallback chains across providers for reliability. — [LLM Routing and Model Cascades](https://tianpan.co/blog/2025-11-03-llm-routing-model-cascades)

### Inferences
- The pattern is architecturally mainstream (treated as a known/expected design in 2026 agent-harness discourse), but the "criteria for good enough" question is mostly answered informally/anecdotally in the blog-post layer (retry limits, vague "stuck" detection) rather than with a published, reproducible rubric — rigor on that specific sub-question currently lives more in academic cascade/routing papers (which define escalation via calibrated confidence/verifiers) than in agent-project writeups.
- Devin's "local-to-cloud handoff" is a useful cautionary data point: it shows that "local + cloud" doesn't always mean "small model + large model" — sometimes it just means "same model tier, different compute location." Hermes's actual target pattern (cheap local tool-execution tier escalating to a materially more capable cloud model) is closer to the classic LLM-cascade/routing literature than to Devin's design.

### Gaps
- Found no large, named production agent project (OpenHands/OpenDevin, Open Interpreter, Continue.dev, AutoGPT) with a public engineering writeup that documents a specific, numeric threshold they used to certify a local model as "good enough" for the routine execution tier. Search for Continue.dev/OpenHands-specific tiering writeups did not surface a dedicated case study within the tool-call budget for this task.
- No r/LocalLLaMA thread was directly retrieved (search results returned adjacent blog/GitHub content rather than an actual Reddit thread) — community-discussion-specific sourcing for this exact question is weaker than blog/academic sourcing.

## What specific failure modes occur when a local model is too small for an agentic tool-calling role?

### Takeaway
The dominant failure modes in real test logs are not malformed JSON syntax per se, but judgment failures: refusing to act and asking for confirmation instead of calling a tool, hallucinating an answer instead of invoking an available tool, emitting a tool call as narrated plain text instead of a structured call, and — most costly — getting stuck in long unproductive retry loops repeating the same broken call.

### Cited Findings
- In a 7-model test of local models driving a Rust coding agent, three of seven models failed outright: `qwen2.5:14b` made an **incorrect text match in an edit operation**; `qwen2.5:7b` **declined to execute and asked the user for confirmation instead of acting**; `qwen2.5-coder:14b` **emitted JSON as plain narrative text rather than a structured tool-call API call**. Overall success rate was 4/7 (57%). — [What Happens When Local LLMs Fail at Tool Calling — Testing 7 Models with a Rust Coding Agent](https://dev.to/kuroko1t/what-happens-when-local-llms-fail-at-tool-calling-testing-7-models-with-a-rust-coding-agent-cep)
- The most severe failure in that same test was a **retry loop**: `qwen3:14b` consumed roughly 30K tokens repeatedly retrying the exact same broken tool call before the author fixed it by adjusting the system prompt — i.e., a capability gap manifested as a runaway cost/latency problem, not just a correctness problem. — [What Happens When Local LLMs Fail at Tool Calling](https://dev.to/kuroko1t/what-happens-when-local-llms-fail-at-tool-calling-testing-7-models-with-a-rust-coding-agent-cep)
- The author's own framing: "model generation matters more than size" — all three `qwen2.5` variants (7B and 14B) failed while the newer `qwen3` family (8B and 14B) and `glm-4.7-flash` (19B) and `devstral-small-2` (24B) succeeded, showing generation/training lineage predicts success better than parameter count. — [What Happens When Local LLMs Fail at Tool Calling](https://dev.to/kuroko1t/what-happens-when-local-llms-fail-at-tool-calling-testing-7-models-with-a-rust-coding-agent-cep)
- Docker's own tool-calling evaluation (21 models, 3,570 tests) found parameter count is a weak predictor on its own: Llama 3.3 **70B** scored only **0.607**, while Qwen3 **14B** scored **0.971**, nearly matching GPT-4's **0.974**; Gemma 3 **4B** scored only 0.733 despite being purpose-built-ish for the size class. — [The biggest local LLM on your machine is useless if it can't call a single tool](https://www.xda-developers.com/biggest-local-llm-machine-useless-cant-call-single-tool-how-many-parameters/)
- A specific hallucination-over-tool-use failure mode: with Llama 3.2 3B on a complex task, "it would reason partway through a problem, acknowledge it needed information it didn't have, and then hallucinate an answer instead of reaching for the tools" — despite that model performing acceptably on simpler benchmark tool-calling tests. The author's conclusion: "reasoning without tool calling is dead weight." — [The biggest local LLM on your machine is useless if it can't call a single tool](https://www.xda-developers.com/biggest-local-llm-machine-useless-cant-call-single-tool-how-many-parameters/)
- A dedicated tool-calling benchmark (21 models from 0.27B–3.8B, CPU-only, 3 test rounds) found that raw JSON-formatting / simple single-tool dispatch is "a solved problem at every size from 270M" parameters upward — the harder failure mode for small models is **judgment**: "deciding whether to act at all." Most sub-4B models failed specifically when prompts contained misleading keywords or required broader context awareness to decide a tool call was (or wasn't) appropriate — i.e., false positives/negatives on *whether* to call a tool, not malformed syntax when they do call one. — [tool-calling-benchmark README](https://github.com/MikeVeerman/tool-calling-benchmark)
- Reliability is also decoding/sampling-sensitive, not just architecture-sensitive: in the same benchmark, scores shifted meaningfully between 3-run and 20-run samples of the same model/prompt — "seven models changing by 0.05+ points" — meaning a model that looks reliable on a small smoke-test can still have real tail-failure variance. Separately, another source notes production-load success rates for models hitting 85% in isolated single-shot tests often degrade to 60–70% under real production load, and recommends treating an **80% success rate on a 5–10 trial suite at production quantization/inference settings** as the bar before calling a model production-ready. — [tool-calling-benchmark README](https://github.com/MikeVeerman/tool-calling-benchmark); [Testing local model tool use reliability](https://theneuralbase.com/function-calling/learn/intermediate/testing-local-model-tool-use-reliability/)

### Inferences
- For Hermes's purposes, the practically dangerous failure modes to design around are not "the model writes invalid JSON" (solvable with constrained decoding / schema validation at nearly any model size) but (a) the model silently declining to act and asking for confirmation when it should just call the tool, (b) the model fabricating a plausible-looking answer instead of invoking an available tool, and (c) runaway retry loops on a bad call that burn tokens/time without ever escalating — all three are "judgment" failures a schema validator won't catch, and all three are exactly the signals a router/judge should watch for to trigger escalation to the cloud tier.
- Benchmarking a candidate local model with only 3–5 trial runs is likely to overstate its real-world reliability; the data suggests needing ~20 trials per task type, at the actual quantization/inference settings intended for production, to get a trustworthy pass-rate estimate.

### Gaps
- I attempted to fetch a specifically relevant academic paper — "Beyond Fluent Generation: A CPU Reliability Benchmark for MCP-Style Tool Calling in Sub-2B Small Language Models for Edge Deployment" (arXiv:2609.07370) — but the fetch tool could not extract readable text from the PDF (binary/compressed stream data only), so its specific reliability numbers and failure-mode taxonomy could not be verified or cited here. This is a gap; the paper's title/abstract suggests it is directly on-topic and worth a human follow-up read.

## Is there guidance or consensus on a practical minimum model size/capability for reliable basic tool-calling?

### Takeaway
There is no consensus on a hard parameter-count threshold — multiple independent benchmarks explicitly reject "bigger = more reliable" and instead point to training lineage/tool-call fine-tuning as the dominant factor; the closest thing to a consensus number is a recommended **validation bar** (roughly 80%+ success over repeated trials at production settings) rather than a model-size cutoff.

### Cited Findings
- "Parameter count tells you almost nothing about whether a model will reliably call the right tool when you ask it to do something." A 600M model (`qwen3:0.6b`) scored 0.880 vs. a 3.8B model (`phi4-mini`) scoring only 0.780 in the same evaluation; separately, models near 1.4B ranged from 0% to 79% success depending on checkpoint, while a 0.5B Qwen checkpoint reached 72% under greedy decoding — the spread within a size class is larger than the spread across size classes. — [Testing local model tool use reliability](https://theneuralbase.com/function-calling/learn/intermediate/testing-local-model-tool-use-reliability/)
- Confirmed independently by Docker's 21-model/3,570-test evaluation: Qwen3 14B (0.971) essentially matched GPT-4 (0.974) while Llama 3.3 70B (5x the parameters) scored only 0.607 — model family/training for tool-use beat raw scale. — [The biggest local LLM on your machine is useless if it can't call a single tool](https://www.xda-developers.com/biggest-local-llm-machine-useless-cant-call-single-tool-how-many-parameters/)
- And again in the 21-model CPU-only benchmark (0.27B–3.8B range): `qwen3:1.7b` was the top performer at 0.960, `lfm2.5:1.2b` scored 0.920 at the best speed/quality ratio (1,567ms latency), and `qwen3:0.6b` scored 0.880 — all beating several larger models in the same test suite. The README's explicit conclusion: "simple, unambiguous tool dispatch is a solved problem at every size from 270M" parameters; what actually separates models is judgment under ambiguity, not raw dispatch mechanics. — [tool-calling-benchmark README](https://github.com/MikeVeerman/tool-calling-benchmark)
- For 2026 "best local LLM for agentic tool calling" recommendations by hardware tier: Qwen3.6-35B-A3B or GLM-4.7-Flash for 24–32GB GPUs, Qwen3.5-9B for 8–16GB, and gpt-oss-120b or Mistral Small 4 for ~128GB machines — i.e., current practitioner guidance sizes the model to available hardware within the "trained for agentic/tool-use" model families, rather than citing a universal minimum. — [Best Local LLM for Agents and Tool Calling (2026)](https://vdf.ai/blog/best-local-llm-for-agents-tool-calling/)
- Practical validation guidance: run a 5–10 trial suite at the exact quantization and inference settings intended for production; treat an 80% production-threshold success rate as essential, because models that hit 85% in isolated/clean tests often regress to 60–70% success under real production load. — [Testing local model tool use reliability](https://theneuralbase.com/function-calling/learn/intermediate/testing-local-model-tool-use-reliability/)

### Inferences
- The actionable "minimum capability" guidance for Hermes is not a parameter count but a selection + validation procedure: prefer model checkpoints explicitly fine-tuned for tool/function calling within whatever size fits the hardware budget (Qwen3 family and similarly agentic-tuned checkpoints repeatedly outperform larger generalist models like Llama 3.3 70B across three independent sources), then validate that specific checkpoint/quantization with a ~20-trial-per-task-type suite and require roughly 80%+ success before trusting it as the routine tier, expecting some additional regression once it is handling real production load and edge-case phrasing.
- Given three separate sources now converging on roughly the same picture (parameter count weakly correlated, training lineage strongly correlated, judgment-under-ambiguity is the real bottleneck), this finding looks solid rather than a one-off anecdote.

### Gaps
- The sub-2B edge-deployment paper (arXiv:2609.07370) that appears most directly on-point for a hard minimum-size claim could not be read (PDF text extraction failed) — see gap noted in the previous section. A follow-up fetch via a different method (e.g., an HTML abstract mirror or ar5iv) might recover its numbers and is worth doing before finalizing Hermes's model choice.
- No source gave a clean "below X billion parameters, reliability categorically drops off" statement — this is a genuine absence of consensus, not just a gap in my search, since multiple benchmarks explicitly argue against such a threshold existing.

## Are there cost/latency studies showing the benefit of small-local + large-cloud two-tier routing, specifically a "router" or "complexity-based escalation" pattern?

### Takeaway
Yes, there is a real academic/industry literature on LLM cascade and routing architectures with cost/latency framing, but most of the strongest numeric claims I could verify came from one synthesized industry blog post rather than from the underlying academic papers themselves, since several of the most relevant arXiv PDFs could not be parsed by my fetch tool — treat the specific percentages below as directionally credible but not independently cross-checked against primary academic sources.

### Cited Findings
- Cascaded inference is described in the academic literature as "serving most requests with a small model and escalating hard cases to a large one," explicitly framed as optimizing both cost and latency simultaneously (distinct papers: UCCI calibrated-uncertainty cascade routing, Cascadia cascade serving system, Signed Rescue Routing harm-aware cascades) — confirming this is an active, named research area, though I was not able to extract full-text numeric results from these PDFs directly (see Gaps). — [UCCI: Calibrated Uncertainty for Cost-Optimal LLM Cascade Routing](https://arxiv.org/html/2605.18796); [Cascadia: An Efficient Cascade Serving System for Large Language Models](https://arxiv.org/pdf/2506.04203); [Signed Rescue Routing](https://arxiv.org/pdf/2609.07786)
- A cascade's effective cost is well modeled as `cost ≈ cheap_model_cost + verifier_cost + (escalation_rate × expensive_model_cost)`, and critically, "even a small escalation rate of 1–3% can erase most cascade savings" — meaning the economics of this architecture are highly sensitive to how often the router/verifier decides escalation is needed, which puts a premium on an accurate "is this routine or complex" classifier rather than on cascade mechanics alone. — [LLM Routing and Model Cascades: How to Cut AI Costs Without Sacrificing Quality](https://tianpan.co/blog/2025-11-03-llm-routing-model-cascades)
- Frontier-model pricing is characterized as roughly 5x costlier than efficient alternatives in the same blog's example (~$5 vs. ~$1 per million input tokens), and "with proper routing, you can maintain 95% of frontier model quality while routing 85% of queries to cheaper models, achieving cost reductions of 45–85%." — [LLM Routing and Model Cascades](https://tianpan.co/blog/2025-11-03-llm-routing-model-cascades)
- Routing (classify-then-pick-one-model) has materially lower latency overhead than cascading (try-cheap-then-verify-then-maybe-retry): embedding-based routers add roughly 2–8ms before the single chosen model call, versus a cascade which always pays for the cheap-model attempt plus a verifier step on every single request, before potentially paying for the expensive model too. — [LLM Routing and Model Cascades](https://tianpan.co/blog/2025-11-03-llm-routing-model-cascades); [Why LLM Cascades Fail for Interactive Apps — Use Router](https://dev.to/nainikmehta/why-llm-cascades-fail-for-interactive-apps-use-router-leg)
- Semantic caching (deduplicating near-identical repeated queries before any model call) is cited as delivering "3.4x latency reduction for near-duplicate queries and 123x for exact matches," and is recommended as the first, simplest layer to add before intent-routing or cascading in a tiered agent cost-optimization rollout. — [LLM Routing and Model Cascades](https://tianpan.co/blog/2025-11-03-llm-routing-model-cascades)

### Inferences
- For Hermes's router design, the 1–3%-escalation-rate sensitivity finding is the most actionable number here: it implies the accuracy of whatever decides "is this routine enough for the local model" matters more to overall cost savings than fine-tuning the local model's own raw capability past a reasonable bar — a noisy/trigger-happy escalation classifier will erode savings faster than a mediocre-but-consistent local model will.
- The routing-vs-cascading latency distinction (one model hop vs. cheap-model-attempt-plus-verifier-plus-maybe-retry) suggests Hermes's existing LLM-as-judge router (per project memory, already replacing a keyword heuristic) is the lower-latency architectural choice compared to a "try local first, verify, then escalate" cascade — worth confirming this matches Hermes's actual implementation.

### Gaps
- Several of the most directly relevant academic papers for hard cost/latency numbers — "Dynamic Model Routing and Cascading for Efficient LLM Inference: A Survey" (arXiv:2603.04445), "Beyond Fluent Generation" (arXiv:2609.07370, sub-2B edge tool-calling) — returned only raw/binary PDF stream data to my fetch tool and could not be read; a search-engine-synthesized summary surfaced some numbers (e.g., "47.2ms vs. 142.3ms mean latency, cost ratio 3.02" for a small vs. large model, and "31% cost reduction at high accuracy on a named entity recognition task") but I could not trace these specific figures to a confirmed primary source URL during this session, so per the instruction to avoid uncited claims, I am flagging them as unverified rather than including them as cited findings. A follow-up with a PDF-capable fetch method (or an HTML/ar5iv mirror of these arXiv IDs) is recommended before relying on those two specific numbers.
- No study was found that measures cost/latency specifically for a coding/ops *agentic tool-calling* workload end-to-end (most of the hard cascade/routing numbers available are from classification or general-QA workloads) — the tool-calling-specific angle of this question is answered more by the benchmark/failure-mode sources in the second and third sections above than by the cost/latency literature itself.
