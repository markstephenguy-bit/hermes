# Phi / Granite / Command-R / Function-Calling Specialists — 64K Native Context Gate

Hard requirement: Hermes Agent rejects any local model that cannot serve **>= 64,000 tokens of real native context**. Per the lesson from the Qwen3-14B incident, native context is checked FIRST, before any benchmark or VRAM math, and `max_position_embeddings` alone is never trusted — `rope_scaling` must also be checked, and when it's `null` but the position-embeddings value looks large, that is a SUSPICIOUS signal requiring a model-card/paper cross-check, not proof of real context.

GPU budget for everything that survives the gate: RTX A4000, 16GB VRAM, weights + KV cache at 64K+ tokens must fit.

**Known llama.cpp caveat (applies to every LongRoPE Phi model, i.e. Phi-4-mini, Phi-4-mini-reasoning, Phi-3.5-mini, Phi-3.5-MoE):** llama.cpp issue [#24823](https://github.com/ggml-org/llama.cpp/issues/24823) — "Phi-3 / Phi-4 LongRoPE: short sequences silently use long-context RoPE factors when the allocated context exceeds `original_max_position_embeddings`" (4096 for Phi-4-mini). llama.cpp picks the long/short RoPE factor set based on the **allocated** context size, not actual sequence length, diverging from the HF reference implementation. Closed as "not planned" (won't be fixed upstream). Practical effect for Hermes: since Hermes would always allocate >=64K context, every Phi LongRoPE model would always run on long-context RoPE factors even for short prompts — behavior is at least consistent, but it is a documented divergence from the reference implementation and is worth being aware of if output quality on short prompts looks off.

- Phi-3.5-mini-instruct: not independently re-measured (expect ~2.2 GB at Q4_K_M given its 3.8B size, consistent with the similarly-sized Phi-3.1-mini-4k's quant listed in search results) — inferred, not directly confirmed

**KV cache at 64K tokens (my own calculation — INFERRED/ESTIMATED, not sourced from a document; formula: `2 (K+V) × layers × kv_heads × head_dim × seq_len × bytes_per_element`, fp16 = 2 bytes):**
- **Phi-4-mini** (32 layers, 8 KV heads, head_dim 128 — confirmed GQA config): ≈ 8.0 GiB fp16 KV cache at 64K tokens. Weights (2.49 GB) + KV cache (≈8 GB) + overhead ≈ **10.5–11 GB total — fits the 16GB budget with headroom.**
- **Phi-3.5-mini** (32 layers, but `num_key_value_heads: 32` = **no GQA reduction**, full multi-head attention, head_dim 96 — confirmed from config): KV cache at 64K balloons to roughly **~24 GiB fp16** — this alone exceeds the 16GB budget before even adding weights. Would require non-default KV-cache quantization (e.g. Q4 KV cache, roughly ÷4 → ~6 GB) to fit, which is itself a caveat/non-default workaround. **Flagged as a VRAM risk — Phi-4-mini's real GQA config is a materially better fit than Phi-3.5-mini's for this exact reason, despite both passing Step 1 identically.**
- **Granite-4.0-H-Tiny**: KV-cache math does not apply uniformly — this is a hybrid Mamba2/attention model where only a small minority of the 40 layers are full-attention (IBM's own description places full-attention layers at specific indices, e.g. 4 of 40 layers in the H-Small variant; the exact count for H-Tiny specifically was not independently confirmed). Because Mamba2 layers carry a small fixed-size recurrent state instead of a context-length-scaling KV cache, total memory growth with context length is far smaller than a standard transformer of comparable size — consistent with IBM's own claim of "over 70% reduction in memory usage... in long-context... workloads." Weights alone are 4.30 GB at Q4_K_M, leaving substantial headroom for KV + overhead within 16GB. **Fits comfortably, likely the most VRAM-efficient option that also passes Step 1 cleanly**, though the exact KV-cache number could not be precisely computed without the full per-layer attention/Mamba layout.
- **Command-R7B**: similarly favorable — architecture is 3 sliding-window-attention layers (window capped at 4096 regardless of total context) to every 1 global-attention layer, so only ~25% of layers scale KV cache with total context length. Exact layer count not confirmed (config gated, 401), so an exact KV-cache number could not be computed — flagged as a gap — but qualitatively this should fit well within 16GB alongside its 5.06 GB Q4_K_M weights.
- **Llama-xLAM-2-8b-fc-r / Functionary-small-v3.2 / Hermes-3-Llama-3.1-8B** (all standard Llama-3.1-8B architecture: 32 layers, 8 KV heads, head_dim 128 — confirmed from config): ≈ 8.0 GiB fp16 KV cache at 64K tokens (same math as Phi-4-mini, since the GQA shape happens to match). Weights ≈ 4.1–4.9 GB. Total ≈ **12–13 GB — fits the 16GB budget with modest headroom.**

## Step 4: llama.cpp support status

### Takeaway
All of the Llama-3.1-8B-based specialists (xLAM-2-8b-fc-r, Functionary-small-v3.2, Hermes-3-Llama-3.1-8B) ride on llama.cpp's mature, long-standing Llama architecture support with no model-specific red flags found. Granite 4's hybrid Mamba2/attention architecture required substantial new llama.cpp engineering that has landed but is comparatively young. Phi's LongRoPE handling has one confirmed, permanently-unfixed divergence from the reference implementation. Command-R7B's llama.cpp status could not be independently confirmed to the same depth (gated config blocked a direct check), though GGUF conversions are clearly circulating.

### Cited findings
- **Phi-4-mini / Phi-4-mini-reasoning / Phi-3.5-mini / Phi-3.5-MoE (LongRoPE family):** llama.cpp issue [#24823](https://github.com/ggml-org/llama.cpp/issues/24823) documents that llama.cpp selects LongRoPE's long-vs-short factor set based on the context size the model is *loaded* with, not the actual sequence length being processed — diverging from the HF reference implementation, which selects per-sequence. Closed "not planned," i.e. permanent, not a bug awaiting a fix. Separately, Phi-4-mini required its own dedicated support PR to llama.cpp — [Feature Request: Support for Phi-4-mini-instruct, issue #12091](https://github.com/ggml-org/llama.cpp/issues/12091) — support exists now (GGUF conversions are widely available from bartowski/unsloth/mmnga) but it was not immediate/day-one.
- **Granite 4.0-H-Tiny / H-Small (hybrid Mamba2/attention, `granitemoehybrid`):** required substantial new llama.cpp infrastructure — Mamba2 layer support, a refactored KV-cache abstraction to support hybrid attention/recurrent caching, and GraniteMoEShared layer support — tracked in [issue #13275](https://github.com/ggml-org/llama.cpp/issues/13275) and landed via [PR #13550 "Granite Four"](https://github.com/ggml-org/llama.cpp/pull/13550) (merged ~May 2025 per the search summary). Support is real and current GGUF quants exist (bartowski's h-tiny/h-small/h-micro repos), but this is meaningfully newer/less battle-tested than standard transformer support, and IBM itself still lists non-hybrid dense alternatives "for users when Mamba2 support is not yet optimized in systems like llama.cpp" per [MarkTechPost's Granite 4.0 coverage](https://www.marktechpost.com/2025/10/02/ibm-released-new-granite-4-0-models-with-a-novel-hybrid-mamba-2-transformer-architecture-drastically-reducing-memory-use-without-sacrificing-performance/).
- **Command-R7B:** No GitHub issues/discussions specifically about llama.cpp problems were found in this pass (absence of evidence, not evidence of absence — this candidate's config itself was gated/401, so verification depth here is shallower than for the others). GGUF quantizations exist from multiple quantizers (bartowski, mmnga, mradermacher, dranger003), implying working llama.cpp conversion support, but no dedicated "is it fully correct" discussion was located.
- **Llama-xLAM-2-8b-fc-r / Functionary-small-v3.2 / Hermes-3-Llama-3.1-8B:** all are straightforward Llama-3.1-8B fine-tunes. No model-specific llama.cpp issues were found; Llama 3.1's architecture and "llama3" RoPE scaling type have been supported in llama.cpp since shortly after Llama 3.1's release and are about as battle-tested as any architecture llama.cpp supports. The main caveat found was **organizational, not technical**: the main MeetKai/functionary GitHub repo is described as deprecated/no longer actively maintained, representing "a very old snapshot that does not represent the current state of the project" — [search summary citing functionary.meetkai.com / GitHub](https://github.com/MeetKai/functionary) — worth weighing against xLAM-2/Hermes-3 if ongoing upstream maintenance matters for Hermes.
- **NexusRaven-V2-13B:** eliminated already on context (16K), so llama.cpp status wasn't pursued in depth. Note only: GGUF quants exist (TheBloke), last HF update reported as "11/4/2026," so the repo isn't abandoned, but it's moot given the Step 1 elimination.

### Gaps
- Command-R7B's `config.json` could not be fetched directly (`CohereForAI/c4ai-command-r7b-12-2024` and `CohereLabs/c4ai-command-r7b-12-2024` both returned HTTP 401 — gated repo requiring authenticated HuggingFace access not available in this session). All Command-R7B figures in this report (context length, architecture, GGUF size) come from secondary sources (Cohere's own docs pages, quantizer HF listings, and aggregator sites), not a primary config/weights check. If Command-R7B becomes the leading candidate, re-verifying its raw config (via an authenticated HF session or `transformers`/`huggingface_hub` with a token) before committing to it is strongly advised, given this is exactly the class of gap that caused the Qwen3-14B incident.
- Exact per-layer attention-vs-Mamba layout for Granite-4.0-H-Tiny specifically (as opposed to H-Small, which was the variant described in the sources found) was not confirmed, so the KV-cache memory-efficiency claim for H-Tiny is qualitative/extrapolated from H-Small's documented layout, not independently confirmed line-by-line.
- No BFCL v4 numbers were locatable for most Step-1/Step-2 survivors (see Step 3 gaps above) — this blocks a fully confident final ranking on tool-calling quality alone; VRAM-fit and architecture robustness are the firmer differentiators from this research pass.
