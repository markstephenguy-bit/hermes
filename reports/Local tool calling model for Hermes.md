# Drop the 35B MoE, go dense

Mark's current Hermes local tier — Qwen3.6-35B-A3B served through ik_llama.cpp with CPU expert-offload — is very likely the wrong pairing for a 16GB RTX A4000 bolted to a 4-core/8-thread Xeon W-2225, and the mismatch gets worse precisely because the local tier's job has already been scoped down to routine tool-calling rather than deep reasoning. The best-supported alternative is a **dense 8–14B model from the Qwen3 family** (Qwen3-14B if VRAM headroom allows, Qwen3-8B if more context/concurrency margin is wanted), quantized to Q4_K_M and run **fully GPU-resident on mainline llama.cpp** (or TabbyAPI/ExLlamaV2 if raw single-stream speed matters more than GGUF-ecosystem flexibility), with ik_llama.cpp dropped entirely. The reasoning is two-pronged: on throughput, a same-hardware-class benchmark shows a fully GPU-resident dense model beating a CPU-offloaded ~30B-A3B MoE by roughly 2.8–6x on an 28-thread CPU — a gap that should only widen on Mark's weaker 8-thread chip — and on reliability, Qwen3.6-35B-A3B specifically has documented reports of malformed tool calls and reasoning loops in long agent chains, which is the exact failure mode Hermes's local tier needs to avoid since Nous Portal is reserved for genuinely hard cases, not for mopping up the local model's own formatting mistakes. Multiple independent benchmarks converge on parameter count being a weak predictor of tool-calling reliability compared to training lineage, which argues for choosing the smallest Qwen3-class checkpoint that passes a real validation suite rather than defaulting to the largest model that fits in VRAM.

## A same-class benchmark already settled the throughput question against Mark's setup

The cleanest available data point comes from a benchmark run on hardware close to Mark's: an RTX 5070 Ti (16GB) paired with a 28-thread CPU and 64GB DDR5. There, a dense Qwen3 8B at Q4_K_M hit **144 tok/s generation and 6,518 tok/s prompt processing** using 7.6GB VRAM, while Qwen3.6-35B-A3B at Q4_K_M with CPU-offloaded experts managed only **52 tok/s generation and 1,041 tok/s prompt processing** despite using less VRAM ([esonhjz/llama-cpp-moe-vram-benchmarks](https://github.com/esonhjz/llama-cpp-moe-vram-benchmarks)). That is a 2.8x generation gap and a 6.3x prompt-processing gap in favor of the fully GPU-resident dense model — and this was measured on a CPU with **28 threads**, more than three times Mark's 8. Token generation under CPU-offload is fundamentally memory-bandwidth-bound, but low thread counts independently cap how well that bandwidth gets saturated, and prompt processing (which matters enormously for an agentic loop that re-ingests tool output after every call) is compute-bound and scales more directly with core count ([carteakey.dev local inference optimization](https://carteakey.dev/blog/local-inference/local-llm-optimization/)). A GitHub issue reporting a CPU-MoE performance regression attributed to "insufficient thread utilization" surfaced even on an 8-core/16-thread Ryzen — nearly double Mark's thread count — reinforcing that this bottleneck shows up well before you get down to 4 physical cores ([ik_llama.cpp issue #1699](https://github.com/ikawrakow/ik_llama.cpp/issues/1699)). No source directly benchmarked Mark's exact 4c/8t + 16GB combination, but every comparable data point points the same direction, and the general rule holds across sources: CPU-MoE offload "normally makes inference slower" once the model could otherwise fit on GPU, and the celebrated 5x MoE speedups only materialize when a model was *overcommitting* VRAM in the first place — which a properly-sized 8–14B dense model does not do ([DEV Community MoE offloading explainer](https://dev.to/someoddcodeguy/understanding-moe-offloading-5co6)). ik_llama.cpp compounds this: its entire value proposition is CPU/mixed-offload kernel efficiency, which is irrelevant (and in some reports actually *slower* than mainline llama.cpp) once the target model is fully GPU-resident, and the fork's hardware support matrix is narrower than mainline's ([libhunt ik_llama.cpp vs llama.cpp](https://www.libhunt.com/compare-ik_llama.cpp-vs-llama.cpp); [ikawrakow/ik_llama.cpp](https://github.com/ikawrakow/ik_llama.cpp)).

## The MoE's speed advantage and its reliability problems share a root cause

Beyond raw speed, there is a documented, architecture-level reason to distrust a large active-sparse MoE for exactly the role Hermes assigns its local tier. A developer directly comparing a 35B MoE coding model against a dense Qwen3.6 27B found the MoE **3x faster in single-shot generation** (246 vs 71 tok/s) but hit five distinct multi-step agent failures across a 112-case suite — forgetting dependencies while claiming completion, contradictory assertions, mid-task abandonment, and calling undefined functions while declaring success — and concluded "the source of MoE's speed and the cause of its failures in agent work turned out to be the same thing," attributing it to the thinner cross-turn state-carrying capacity that comes from only ~3B parameters being active per token ([wada-dev.com, MoE vs dense for local LLM agent tasks](https://wada-dev.com/en/blog/moe-vs-dense-local-llm-agent-tasks/)). That precedent lines up directly with reports specific to Mark's exact model: Qwen3.6-35B-A3B is called out as "more prone to reasoning loops and malformed tool calls that interrupt long agent runs" compared to its predecessor checkpoint, with a separate note that enabling Multi-Token Prediction further degrades tool-call formatting because speculative decoding interferes with producing well-formed JSON ([allanchan339.github.io, Qwen3.6-35B-A3B tool-calling notes](https://allanchan339.github.io/bug-fixes/2026/04/20/Qwen36-35B-A3B-tool-calling.html)). One cited measurement went further, showing a Qwen 3.6 35B model emitting unparseable tool-call wrappers on roughly **70% of runs** (0 of 10 successful) in a specific serving configuration ([NVIDIA/NemoClaw issue #2733](https://github.com/NVIDIA/NemoClaw/issues/2733)). This matters more for Hermes than for a generic coding assistant, because the whole premise of the two-tier design is that Nous Portal catches *hard* cases — not that it exists to clean up routine tool calls the local model mangled. A local model that is both slower (CPU-offload penalty) and less format-reliable (thin MoE state) on exactly the easy, high-frequency work it was supposed to own is paying a cost on both axes of the design at once.

## Parameter count is the wrong lever; training lineage and validated reliability are the real ones

Three independent benchmarks converge on the same counter-intuitive finding: raw parameter count barely predicts tool-calling reliability. Docker's 21-model, 3,570-test evaluation found Llama 3.3 **70B** scored only 0.607 while **Qwen3-14B scored 0.971**, essentially matching GPT-4's 0.974 ([Docker/xda-developers tool-calling evaluation](https://www.xda-developers.com/biggest-local-llm-machine-useless-cant-call-single-tool-how-many-parameters/)). A second benchmark testing models down to 0.27B found "simple, unambiguous tool dispatch is a solved problem at every size from 270M parameters upward," with the real differentiator being judgment under ambiguity — deciding *whether* to call a tool at all — rather than JSON-formatting mechanics ([MikeVeerman/tool-calling-benchmark](https://github.com/MikeVeerman/tool-calling-benchmark)). A third found a 600M Qwen3 checkpoint outscoring a 3.8B Phi-4-mini (0.880 vs 0.780), and noted that within-size-class variance exceeds across-size-class variance ([theneuralbase.com, testing local model tool use reliability](https://theneuralbase.com/function-calling/learn/intermediate/testing-local-model-tool-use-reliability/)). What *does* predict reliability is training lineage: across every source, the Qwen3 family recurs as the most consistently cited "stable tool-caller" at every size tier, with community guidance explicitly framing Qwen3-8B as "best on 8–12GB" and Qwen3-14B as "most reliable for tool calls per GB" on 12–16GB cards — i.e., squarely in Mark's VRAM budget without any CPU offload ([tomodahinata.com Qwen3 agent writeup](https://tomodahinata.com/en/blog/qwen3-agent-tool-use-function-calling-qwen-agent-production); [localaimaster.com best Ollama models for agents](https://localaimaster.com/blog/best-ollama-models-for-agents)). At Q4_K_M, Qwen3-14B needs roughly 9–9.5GB VRAM and Qwen3-8B roughly 5GB, leaving the remaining 7–11GB of the A4000's 16GB for KV cache and context headroom ([willitrunai.com Qwen3-14B](https://willitrunai.com/models/qwen-3-14b)) — comfortably inside budget with zero dependency on the weak CPU. Since routine agentic failures in real test logs are dominated by judgment errors (declining to act, hallucinating instead of calling a tool, or looping on a broken call) rather than pure syntax errors ([dev.to kuroko1t, 7-model Rust agent test](https://dev.to/kuroko1t/what-happens-when-local-llms-fail-at-tool-calling-testing-7-models-with-a-rust-coding-agent-cep)), the right selection process for Hermes is not "pick the biggest model that fits" but "pick a Qwen3-tuned checkpoint sized to the hardware, then validate it empirically": run roughly 20 trials per tool/task type at the exact production quantization and require an ~80% success floor, since models that look reliable on a 3–5-trial smoke test routinely regress 15–25 points under real load ([theneuralbase.com validation guidance](https://theneuralbase.com/function-calling/learn/intermediate/testing-local-model-tool-use-reliability/)).

## The engine choice should follow the model, not the other way around

Once the model is fully GPU-resident, ik_llama.cpp has nothing left to offer — its entire reason for existing is CPU/mixed-offload kernel efficiency, which becomes moot (and in some user reports actively slower) for a 100%-GPU workload ([libhunt comparison](https://www.libhunt.com/compare-ik_llama.cpp-vs-llama.cpp)). Mainline llama.cpp is the pragmatic default: it natively supports the `hermes` tool-call parser format that Qwen3 was trained against, its GGUF ecosystem is the broadest for model/quant availability, and its concurrency model (`--parallel` slots with continuous batching) is adequate for the "a few overlapping agent turns from one household," not "many simultaneous external users," scale that Hermes actually needs — stated guidance puts llama.cpp's comfortable zone at 1–10 concurrent users before vLLM's throughput-per-VRAM pulls meaningfully ahead ([Big Iron llama.cpp multi-user guide](https://www.bigiron.cc/guides/llamacpp-server-multi-user-batching-and-queueing-patterns)). If Mark wants the fastest possible single-stream latency rather than llama.cpp's simplicity, TabbyAPI on ExLlamaV2 is the next option worth testing: it is repeatedly cited as the fastest single-user generation engine on consumer/workstation NVIDIA GPUs, and its paged-attention concurrent-batching path is explicitly gated to Ampere-and-newer GPUs, which the A4000 satisfies — the tradeoff is a narrower EXL2-only quant ecosystem instead of GGUF ([local-llm.net inference engine comparison](https://www.local-llm.net/compare/inference-engines-2026/); [TabbyAPI docs](https://deepwiki.com/theroyallab/tabbyAPI)). vLLM and SGLang are worth ruling out for this specific role rather than reaching for by default: vLLM carries real CUDA-context VRAM overhead (600MB–1.2GB before any weights load) and currently has open, unresolved bugs where the `hermes` tool-call parser silently breaks in streaming mode and the Qwen3 parsers fail to populate `tool_calls` at all for some Qwen2.5-Coder variants ([vLLM tool calling docs](https://docs.vllm.ai/en/latest/features/tool_calling/); [vLLM issue #31871](https://github.com/vllm-project/vllm/issues/31871)) — exactly the model families Hermes would be serving. This also lines up with Hermes's own operational history: the project already had to cap `max_concurrent_sessions` at 3 after a single-slot crash, so treating vLLM's concurrency/VRAM behavior as a known risk rather than an obviously-safe upgrade is consistent with what Mark has already seen in production, not a new caution being introduced here.

## Conclusion

The core insight this research surfaces is that "3B active parameters" was never the right way to read Qwen3.6-35B-A3B's fit for a 16GB-GPU-plus-weak-CPU box — the full ~35B of weights still has to live somewhere, and once a meaningful share lands on a 4-core CPU, the model is simultaneously slower *and* less format-reliable than a dense 8–14B model that never leaves the GPU, for a role (routine tool execution) that was explicitly scoped to need neither extra reasoning depth nor extra parameter capacity. The cloud-escalation design this sits inside only strengthens the case for going smaller and more disciplined locally rather than bigger: cascade/routing economics are highly sensitive to escalation accuracy (a 1–3% bad-escalation rate erases most of the savings), which means the priority for the local tier should be consistent, validated format-reliability on routine calls — something a well-tuned Qwen3-8B/14B on mainline llama.cpp is better positioned to deliver than a CPU-starved 35B MoE, leaving Nous Portal to do what it was actually brought in for.
