# Two gateways earn the single-container crown

No official gateway exists from Anthropic, OpenAI, Google, or the Model Context Protocol steering group itself — the MCP standards body's own registry explicitly "is not designed for self-hosting" ([modelcontextprotocol.io/registry/about](https://modelcontextprotocol.io/registry/about)) — so the real field is a mix of solo-maintainer open-source projects and one venture-funded entrant. Against the five criteria (singular, powerful, long-lasting, fast, cross-client), **MCPHub — deployed via the hwdsl2/UplinkCrate single-container wrapper — is the strongest overall fit** for fronting custom self-written MCP servers from Claude Code, Antigravity, ChatGPT's connector, and a generic bearer-token client, combining the richest auth/RBAC/hot-reload feature set found in this research with the highest commit velocity of any candidate (20+ commits in the week before this report). **mcp-gateway (mspstack) is the runner-up**: it can also run as one container, documents exact Claude Code registration syntax, confirms live hot-reload, and ships a purpose-built OAuth 2.1 + dynamic-client-registration facade that matches exactly how ChatGPT's connector wants to be talked to — but its entire user base is effectively one developer with one GitHub star, a real long-term-risk signal MCPHub doesn't carry. A pivotal finding that reshapes the whole comparison: ChatGPT's remote-connector UI **does not require OAuth** — it offers a plain static "Access token / API key" bearer-token mode alongside OAuth ([OpenAI developer docs](https://developers.openai.com/api/docs/guides/custom-mcp-server)), so the simpler bearer-token gateways in this field are not automatically disqualified from the hardest client in Mark's list. Several other names that surface early in web search — MCPJungle, ToolHive's vMCP, IBM's ContextForge, Kong, Portkey, and a cluster of sub-500-star repos — all have real merits but also real, documented weaknesses serious enough to flag before adoption.

## No official or enterprise option fits a home lab

Anthropic donated the MCP protocol itself to the Linux Foundation's new Agentic AI Foundation in December 2025 ([Anthropic news](https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation)), but neither Anthropic, OpenAI, nor Google ships a self-hosted gateway product. The `modelcontextprotocol/servers` repo is just reference example servers, and the official registry's own maintainers state plainly that "the registry maintainers cannot provide support" for self-hosting it ([GitHub](https://github.com/modelcontextprotocol/registry)). Anthropic's "MCP tunnels" feature is a private-network-access mechanism for reaching Anthropic's own products, not a general cross-client aggregator ([DEV Community writeup](https://dev.to/thegatewayguy/anthropics-mcp-tunnels-and-self-hosted-sandboxes-keeping-agents-inside-your-perimeter-5a4d)). The enterprise API-gateway vendors that do offer MCP support are a worse fit for a home lab than they first appear: Kong's "AI MCP Proxy" plugin is gated behind Kong Gateway Enterprise, bolted onto a full API-gateway platform rather than offered as a free-standing MCP-only tool ([Kong AI Gateway docs](https://developer.konghq.com/ai-gateway/)), and Portkey's MIT-licensed MCP Gateway — while genuinely self-hostable and free — has its expanded "Gateway 2.0" MCP capability set still labeled prerelease as of its latest tagged release ([API7.ai comparison](https://api7.ai/ai-gateway-comparison)), meaning the feature set a home-lab user would actually want is still moving under them. This is why the comparison that matters is almost entirely among independent open-source projects.

## Singular is rarer than the marketing claims

Every candidate claims to be "one gateway," but reading the actual Docker Compose files tells a different story. **hwdsl2/UplinkCrate** is the cleanest true single-container deployment: one image bundling Caddy (bearer-token auth) in front of MCPHub, with file-based storage persisted to a volume and no second service ([GitHub repo](https://github.com/hwdsl2/docker-mcp-gateway)). **McpManager** matches it — a single `docker run` command with SQLite baked into the same container, no compose file at all in the repo root ([GitHub README](https://github.com/daniel3303/McpManager)). **mcp-gateway (mspstack)** ships a three-service compose file by default (gateway, OpenBao secrets vault, and a commented-out example upstream), but its own docs confirm OpenBao is optional and a genuine single-container path exists using plain `${VAR}` env-var credentials instead ([docker-compose.yml](https://raw.githubusercontent.com/mspstack/mcp-gateway/main/docker/docker-compose.yml); [standalone-secrets.md](https://raw.githubusercontent.com/mspstack/mcp-gateway/main/docs/standalone-secrets.md)). **MCPJungle**, despite its "one place to manage" pitch, documents a quickstart that is explicitly two containers — a required Postgres 17 service plus the gateway — with no primary-source confirmation that its alternative "single binary" mode can run without Postgres ([docker-compose.yaml](https://raw.githubusercontent.com/mcpjungle/MCPJungle/main/docker-compose.yaml)). **ToolHive's vMCP**, in its newer local CLI mode, is itself a single Go process with an embedded SQLite index and no external database ([docs/arch/vmcp-local.md](https://github.com/stacklok/toolhive/blob/main/docs/arch/vmcp-local.md)) — but vMCP is explicitly an aggregator *over* backend MCP servers that are expected to already be running as their own ToolHive-managed containers, so "one container" only describes vMCP's own process, not the full footprint of fronting several custom servers. **unified-mcp-gateway** is the clearest violator of its own branding: its compose file defines three required services — Postgres, a Rust/Axum server, and a separate React dashboard — confirmed directly from the repo, not just marketing copy ([docker-compose.yml](https://github.com/sidpad03/unified-mcp-gateway/blob/main/docker-compose.yml)). **IBM's ContextForge** sits in the middle: a minimal single-container mode exists, but the documented fuller deployment adds Postgres, Redis, and Nginx, so the "real" recommended path is heavier than one container.

## Auth and RBAC depth separate contenders from toys

On raw feature depth, **MCPHub** and **mcp-gateway** pull well ahead of the field. MCPHub documents OAuth 2.0 in both client and server modes, JWT+bcrypt accounts, social login via Better Auth, per-user encrypted credential binding, and granular tool/prompt/resource visibility controls, plus confirmed "hot-swappable config" letting servers be added or removed without downtime ([GitHub repo](https://github.com/samanhappy/mcphub)). It even ships a guarded `allowAuthorizationPassthrough` opt-in specifically useful for connector-style clients that forward their own Authorization header ([GitHub PR #1453](https://github.com/samanhappy/mcphub/pull/1453)). **mcp-gateway** counters with an OAuth 2.1 resource-server mode against Entra ID or any OIDC provider, a self-hosted dynamic-client-registration (DCR) facade implementing RFC 8414/7591 so a client can connect with nothing but a URL, role-based access (viewer/editor/admin plus custom roles), per-tool allow/deny re-checked at call time, network ACLs tied to tool risk tiers, and a confirmed live hot-reload where connected clients receive a `tools/list_changed` notification the moment an admin adds or removes an upstream — no restart ([README via WebFetch](https://github.com/mspstack/mcp-gateway); [docs/ui-guide.md](https://raw.githubusercontent.com/mspstack/mcp-gateway/main/docs/ui-guide.md)). **ToolHive's vMCP** is architecturally the most sophisticated of all — an embedded OAuth 2.0/2.1 authorization server with Cedar policy-as-code enforcement and multi-IdP federation (GitHub, Google, Okta) ([vMCP concepts](https://docs.stacklok.com/toolhive/concepts/vmcp)) — but the fetched docs never confirm a simple static-bearer-token mode for clients, and a live GitHub issue shows connected client sessions aren't always notified when a backend is removed, a real rough edge in otherwise strong hot-reload support ([GitHub issue #6762](https://github.com/stacklok/toolhive/issues/6762)). By contrast, **MCPJungle** is still pre-OAuth on its own admission — "support for OAuth flow is coming soon" — leaving Bearer-token auth as the only shipped mechanism, albeit with a well-documented tool-group filtering model. **McpManager** covers the basics solidly (Bearer/API-key/Basic/env auth, claims-based authorization, a real-time filterable log viewer backed by Serilog) but documents no hot-reload and no role hierarchy. **unified-mcp-gateway** claims a feature set on paper (JWT+API key, owner/operator/viewer RBAC, a glob-pattern policy engine, automatic tool risk classification, Prometheus metrics) that reads as comparably rich to the leaders — but every one of these claims is self-reported by its solo author with no independent or third-party verification found anywhere, a meaningful gap for a project whose entire pitch is security.

## Stars mislead — recent commit activity is the real signal

Star counts and actual maintenance health diverge sharply across this field as of November 2026. **ToolHive is backed by Stacklok**, a venture-funded software-supply-chain-security company (Series A, $17.5M from Accel and Madrona, founded 2023, with a track record of donating its "Minder" project to the OpenSSF) ([Crunchbase via WebSearch](https://www.crunchbase.com/organization/stacklok); [The New Stack](https://thenewstack.io/stacklok-donates-minder-security-project-to-openssf/)) — the toolhive repo shipped a release dated the same day as this research, November 3, 2026 ([releases](https://github.com/stacklok/toolhive/releases)). **samanhappy/mcphub** has no visible company behind it but is by far the most actively worked-on repo in this entire comparison: 2.6k stars, 1,003 total commits, and 20+ commits in just the five days before this report (Oct 29–Nov 3, 2026) ([GitHub repo](https://github.com/samanhappy/mcphub)). **MCPJungle** is the steadiest mid-tier option — backed by its own GitHub org, 1.5k stars, ten tagged releases from March through October 30, 2026, with commits landing as recently as November 3 ([releases](https://github.com/mcpjungle/MCPJungle/releases)). **mcp-gateway (mspstack)** has almost no community footprint — 1 star, 1 fork, a single contributor — but has released roughly weekly since August 2026 through its latest tag (v0.22.0, October 12, 2026) ([Tags API](https://api.github.com/repos/mspstack/mcp-gateway/tags)), making it active-but-unproven rather than abandoned. **hwdsl2/UplinkCrate** is a brand-new wrapper (first commit July 2026, 5 stars, one tag) that is being actively committed to right now but carries real future-abandonment risk as a thin one-person shim around someone else's engine ([GitHub repo](https://github.com/hwdsl2/docker-mcp-gateway)). Two projects show clear abandonment signals: **McpManager**'s `main` branch has had no commits since May 27, 2026 and no release since v1.1.2 (May 16, 2026) — over five months stale ([commit history](https://api.github.com/repos/daniel3303/McpManager/commits)) — and **unified-mcp-gateway** has gone quiet since September 30, 2026, a month-plus gap for a project with only 16 stars and a single human contributor pairing with an AI coding assistant ([commits/main](https://github.com/sidpad03/unified-mcp-gateway/commits/main)).

## Every candidate is a deterministic proxy, on faith rather than benchmarks

All seven primary candidates are architecturally plain HTTP relays/routers in their default configuration, with no LLM reasoning step in the core request path — this is confirmed by direct description for MCPHub, MCPJungle, McpManager, mcp-gateway, ToolHive vMCP, unified-mcp-gateway, and IBM ContextForge alike. The only deviations are opt-in, non-default features: MCPHub's "Smart Routing" uses vector-embedding semantic search over tool descriptions at an explicit `/mcp/$smart` route, layered on top of the base deterministic proxy and requiring separate database setup to enable ([docs.mcphubx.com](https://docs.mcphubx.com/features/smart-routing)); ToolHive's vMCP has an equivalent opt-in "MCP Optimizer" that defaults to a local SQLite FTS5 keyword tier and only spins up an embedding-model container if a Tier-2 flag is explicitly set ([docs/arch/vmcp-local.md](https://github.com/stacklok/toolhive/blob/main/docs/arch/vmcp-local.md)). Critically, **no candidate in this research publishes a single quantitative latency or throughput benchmark** in any primary source — MCPHub, UplinkCrate, MCPJungle, McpManager, and mcp-gateway all have an explicit documented absence of performance numbers, and the only speed claims found at all (unified-mcp-gateway's self-reported "~15MB binary, starts instantly, handles thousands of concurrent connections") are author-stated and unverified by any independent load test. FAST should be read as "architecturally satisfied by default, unmeasured in practice" across the board, not as a differentiator between candidates.

## ChatGPT's bearer-token option rewrites the cross-client calculus

The single most consequential fact uncovered in this research is that **ChatGPT's remote-connector UI does not require OAuth**. OpenAI's own developer guide documents that under "Add custom MCP server," authentication modes include OAuth, "No authentication," and a mixed mode, and explicitly states "if your server expects a Bearer token in the Authorization header, set the Header Name to Authorization and the Value to Bearer `<your-token>`" ([OpenAI developer docs](https://developers.openai.com/api/docs/guides/custom-mcp-server)) — corroborated by multiple independent reports describing a selectable "Access token / API key" mode in the live Settings → Connectors UI that attaches a fixed bearer token with no OAuth, JWT, or JWKS involved ([GitHub issue, agentfront/frontmcp #544](https://github.com/agentfront/frontmcp/issues/544)). This means every bearer-token-based gateway in this comparison is plausibly ChatGPT-compatible, not just the OAuth-heavy ones — though full read-write MCP access is gated to ChatGPT Business/Enterprise/Edu tiers, with Pro capped to read/fetch only, per a search-snippet read of OpenAI's help-center article that could not be directly fetched in this research pass and should be treated as provisional ([help.openai.com, snippet-only](https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt)). Network reachability remains a separate gate: OpenAI's Secure MCP Tunnel exists specifically so a private, behind-NAT home-lab server can connect without a public HTTPS endpoint ([developers.openai.com](https://developers.openai.com/api/docs/guides/custom-mcp-server)). Against this backdrop, **ToolHive is the one candidate explicitly documented as having a ChatGPT problem**: its own client-compatibility matrix puts "ChatGPT Desktop" under "Manual Configuration Required," notes it "only accepts MCP servers over HTTPS" with no command-based config, and warns that the suggested ngrok-tunnel workaround "creates security risks with unauthenticated, publicly-accessible workloads" ([Client compatibility page](https://docs.stacklok.com/toolhive/reference/client-compatibility)). ToolHive does, however, have the best-documented Antigravity support of any candidate — "tested with Claude Code, Gemini CLI, and Google Antigravity," reading `~/.gemini/config/mcp_config.json`, which matches the exact path already registered in this environment ([WebSearch synthesis of client-compatibility docs](https://docs.stacklok.com/toolhive/reference/client-compatibility)). No candidate documents Antigravity/Gemini by name except ToolHive; for the rest, compatibility is inferred from shared MCP-over-HTTP transport, not confirmed. On registering a fully custom, already-running upstream server — the user's core requirement — **MCPJungle has the most precisely documented schema** of any candidate, with explicit `bearer_token`, `headers`, and optional OAuth-client fields in its JSON registration format ([docs.mcpjungle.com guide](https://mcpjungle.mintlify.app/guides/register-http-servers)), while **ToolHive's vMCP has the opposite problem**: the only confirmed custom-server syntax found is an image-based Kubernetes `MCPServer` CRD that ToolHive itself runs from a container image, with no confirmed syntax for pointing at an arbitrary external host:port server already running outside ToolHive's management — a real gap against the user's stated need.

Several names that look appealing in general search should be flagged before anyone adopts them. **McpManager** and **unified-mcp-gateway** both show real abandonment signals (five-plus months of silence each) despite initially attractive feature lists — unified-mcp-gateway in particular markets itself as a "unified" single gateway while its own compose file requires three containers, and every one of its RBAC/audit/policy claims is self-reported with no third-party verification found anywhere. **Portkey's MCP Gateway** is genuinely self-hostable and MIT-licensed, but its expanded MCP capability set ("Gateway 2.0") is explicitly labeled prerelease in its own documentation — not stable enough to anchor on. **Kong's AI MCP Proxy** requires Kong Gateway Enterprise, making it a paid-plugin feature of a full API-gateway platform rather than a free, purpose-built MCP tool. The **official MCP Registry** is the clearest case of a trustworthy-sounding source turning out to be the wrong tool entirely — its own maintainers state it "is not designed for self-hosting." Finally, a cluster of sub-500-star repos surfaced in search (mcpproxy-go at roughly 350–380 stars, MikkoParkkola/mcp-gateway at ~83, R0Wi/mcp-gateway at ~0, cuongdev/mcp-gateway at ~3, and an unverified "anythingmcp" at ~200) all list feature sets that read as comparably sophisticated to the major players — cuongdev's README in particular claims OIDC, Casbin RBAC/ABAC, circuit breaking, and a 42-connector catalog despite only 3 stars — a mismatch between claimed capability and adoption signal that should read as a caution flag, not a hidden gem, until proven otherwise.

## Conclusion

The practical recommendation is **MCPHub, run through the UplinkCrate single-container packaging** (or MCPHub directly with its own file-based config if the thin wrapper's own newness is a concern): it is the only candidate that pairs a genuinely singular deployment with the deepest auth/RBAC/observability/hot-reload feature set found anywhere in this research, backed by a commit velocity that makes abandonment risk low even without corporate backing. Register custom self-written servers in its `mcp_settings.json` (confirmed stdio syntax, streamable-HTTP syntax moderately-confident but not independently verified against MCPHub's own docs site), and lean on the guarded `allowAuthorizationPassthrough` setting if ChatGPT's connector needs header forwarding beyond a static bearer token. **mcp-gateway (mspstack)** is the runner-up precisely because it would be the top pick on pure engineering merit — confirmed hot-reload, confirmed Claude Code CLI syntax, and an OAuth 2.1/DCR facade that happens to match ChatGPT's actual (not assumed) auth model — if not for the stark long-term risk of a one-star, one-contributor repo. The deeper lesson from this research is that the field has temporarily inverted the usual signal: the best-funded, most clearly "long-lasting" option (ToolHive/Stacklok) is the weakest fit for this specific home-lab ask, because its architecture is built around aggregating ToolHive's *own* managed workloads and an OAuth-first client model, leaving ChatGPT explicitly unsupported out of the box and arbitrary custom-upstream registration undocumented — a reminder that "who built it" and "does it do the one thing I need" are genuinely separate questions in this ecosystem.
